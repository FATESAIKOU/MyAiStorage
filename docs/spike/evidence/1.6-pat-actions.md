## 假綠燈檢查

- 步驟 3 失敗是**權限類**（403 `Write access to repository not granted`／`Resource not accessible by personal access token`），且已用無效 token 對照證明 401 認證錯長得不一樣；步驟 1、2 成功排除「token 根本沒帶上」。
- 步驟 10c／10b 沒有可測對象（artifact／cache 皆 0 筆），照 test-plan 記「無可測對象」而非「不能讀」。
- 步驟 4 修正：一開始把 jq 透傳的 403 JSON 誤讀成「拿到 sha」，重跑 contents GET 確認 403，已在表上更正。
- 步驟 5 執行後已確認兩個 workflow 都回到 `active`（無論 disable 的成功或失敗）；測試窗口內沒有 pending run 被影響。

## 對 design／1.9 的結論

- **住民 token 不能推 contents、不能改 workflow 檔、不能讀 contents／secrets、不能動 repo 與 Actions 設定**——但可以**觸發任何已存在的 workflow（以既有分支／tag）**。
- **它可以 enable／disable workflow、cancel／刪除 run、rerun、讀 run log**；artifact／cache 沒有可測對象。
- 因此：
  1. D2「管理腳本先停 workflow」**不可靠**：住民能把被停用的 workflow 重新啟用（1.6 已證實 enable 可行），管理操作的錯開**必須以 manifest 預檢為主**（與 1.2 M8 的結果綁定；1.9 彙整時一起看）。
  2. **提交流程的 log 屬於住民讀得到的範圍**：被觸發的 workflow 只要有輸出內容，住民就能下載 log。D2 要明文規定 workflow 不輸出 Session 內容、不留 artifact；**1.3 的抹除範圍要涵蓋 Actions log／artifact／cache**（或設計成根本不產生）。
  3. 執行紀錄可被刪除：**稽核不能依賴 Actions 的 run 紀錄**（design 已寫「稽核寫在提交流程自己的 commit 裡」，此結果支持該設計）。
  4. 觸發只能以既有分支／tag——住民無法用自建的 sha／分支（它沒有 contents 權限，push 不進去）當 ref；這限制了觸發面但**不能當安全邊界**（workflow 仍必須被任意觸發也安全）。
- 步驟 5〜8、10 的「可 enable／disable／cancel／刪 run／讀 log」依 test-plan **不算 fail**，屬 caveat（前提是 1.2 的 manifest 預檢 pass）。
