# 1.7e 有沒有可信的結束或封存訊號

- 執行時間：2026-09-26 08:0x〜09:0x UTC（M2 補測見第 2 節末）
- 執行者：impl3；容器 `oc17-main`（arm64）
- 判定：**go-with-caveat**——找到 opencode 既有、可遠端觀測的 `time.archived` 訊號，且它是使用者（或 TUI／API）**明確**操作產生的，不是閒置推測；當版**沒有 CLI 子命令**、只能經 HTTP API 設定（TUI 有封存動作）。封存不禁止後續追加、也不自動解除；補測確認**封存的 Session 仍出現在 `session list`**（CLI 兩種格式與 API 皆在，不會造成同步死角）。建議：以 `time.archived` 當「明確宣告」的管道（D4／3.9 規則見第 3 節）。

## 1. 檢查清單（逐一記錄）

| 檢查項 | 結果 |
|---|---|
| CLI 頂層／`opencode session` 子命令 | **沒有** end／stop／close／archive 指令（`--help` 逐一檢視）；只有 `session list`、`session delete` |
| API 端點表（binary 字串） | `/session/{id}/abort`（只中止生成）、`/session/{id}/fork`、`revert`、`unrevert`、`summarize`、`share`、`init`、`command`、`shell`；**沒有** `/archive` 或 `/end` 端點 |
| DB `session` 欄位 | 有 `time_archived`（與 `time_created`、`time_updated`、`time_compacting` 並列）；`revert`、`parent_id` 也在 |
| DB 值 | 全部測試 Session 的 `time_archived` 初始皆 NULL（`select count(*) … where time_archived is not null` → 0） |
| TUI 介面 | 有 Archive 動作（`common.archive`、`archiveSession`、`session.archive`，sidebar 按鈕）；對應 SDK 的 session update payload `time.archived` |
| 其他狀態 | `event` 表只有 `session.created|updated|deleted`、`message.*`；`session_message`／`session_input` 本次為 0 筆（未使用）；無「ended／closed／idle」欄位 |
| 程序結束 | 不構成訊號（`opencode run` 每次結束都只是 process 結束） |
| 閒置時間 | 不構成訊號（DB 只有時間戳，沒有狀態判定） |

## 2. `time.archived` 是可信（明確）訊號的實測

設定方式（當版唯一可行路徑：HTTP API）：

```bash
$ curl -s -X PATCH "$API/session/$SID?directory=/work" -H 'content-type: application/json' \
    -d '{"time":{"archived":1790410000123}}'
# http=200；回應 .time = {"created":…,"updated":…,"archived":1790410000123}
$ sqlite3 opencode.db "select time_archived from session where id='$SID'"
1790410000123
```

- **觀測方式**（實測一致的兩條）：`GET /session/{id}` 的 `.time.archived`（值為時間戳），以及**同一 API** 的 `GET /session`（清單，每筆含 `time.archived`，`0` 也照實回傳）；`opencode export` 的 `info.time.archived` 亦同。DB `time_archived` 欄位可直接查到同值。
  - 注意：`opencode session list --format json`（CLI）**不輸出** `time.archived`（只到 `updated`），所以同步器要以 API 或 export／DB 觀測，不能只看 CLI list。
- 是**明確**操作：值是指定的時間戳（0 也算設定；見下），不是由閒置或程序結束推測。
- 匯出時 `info.time` 直接帶 `{"created":…,"updated":…,"archived":…}`（archived session 也照常可匯出，內容完整）。

**不自動解除**：對已 archived 的 Session 追加新內容（`opencode run -s $SID` 成功送出新訊息）後，`time_archived` 原值保留（`1790411111111` 未變）。
**解除方式**：同 API 再設為 `0`（或任何值）；`{"time":{"archived":null}}` **不會**清除（回應仍為原值、DB 不變）。

### M2 補測：封存後還在不在 `session list`（2026-09-26 09:0x UTC）

對已封存的 `SPIKE-1.7-S1`（`time_archived=1790420000000`）：

- **CLI `opencode session list`（table）**：**照常出現**（`ses_f235a894effes0cRw74MxQPLBb  SPIKE-1.7-S1`）。
- **CLI `opencode session list --format json`**：**照常出現**；但該輸出的 `time` 物件只有 `created`／`updated`，**不含** `archived`（所以 CLI list 看不出封存狀態，需用 API／export／DB）。
- 數量對照：CLI list 16 筆 vs DB `session` 17 筆（差額是子 Session，不在 list；封存的那筆**有**在 list 內）。
- **API `GET /session`**：照常出現，且帶 `"archived":1790420000000`（全清單中 `time.archived != null` 的恰為這 1 筆）。
- 結論：**封存的 Session 不會被隱藏**，同步器照樣看得到封存之後的追加內容——D4／5.2 的「封存後又追加 → 回到運作中」可以實作；`time.archived` 不會造成同步死角。此結果**不改變** 1.7e 的 go-with-caveat 判定。

## 3. 與 design D4 的關係（建議）

- D4 現行結論「opencode 沒有可信的結束訊號 → 停止中由你或 AI 明確宣告」**仍然成立**：`time.archived` 需要一個明確動作、不是來源應用自然產生的結束訊號。
- 封存後仍可追加、且不會自動解除。**更正**：這與 spec 並不衝突——spec 的規則是「停止中的 Session 又被追加內容時，在 **Agora 這一側**回到運作中」，並不要求來源端自己解除封存。因此 `time.archived` 正好可以當「明確宣告」的**管道**：使用者在 TUI 按封存、AI 用 skill 呼叫 API 的 PATCH。
- 建議（採納 review M2 的對策）：D4 與 3.9 用「`archived > 0` 且封存時間之後沒有新訊息」才判停止中、`archived = 0` 視為沒有封存；停止時間取同步器觀測到的時間（或封存後第一次匯出的快照時間），不要直接信來源端填的值。配合上面的補測：封存不會隱藏 Session，同步器仍可看到後續追加。
