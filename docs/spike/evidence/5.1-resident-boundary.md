# 5.1 住民容器的能力邊界（實測）

- 日期：2026-09-28
- 對象：`resident/`（Mac 上的 opencode，tasks 5.1；`docs/impl/group5-7-modules.md` 第 1 節）
- 設計依據：design D3、ADR 0006、group5-7 第 1.2／1.4 節、PM 決定 1／2（2026-09-28）
- image：`aistorage-resident:latest`（arm64/linux，531 MB；Ubuntu 24.04 + opencode 1.18.32
  + rclone 1.75.1 + Python 3.12.3 + aistorage wheel）
- 容器：`resident/run.sh boundary-1 --profile mac-opencode --model opencode/space-bunny-free`
- **本檔不含任何秘密的值**：只記環境變數的**名稱**、掛載、檔名與計數。
  secret 的比對只用 `grep -r -c -F -f` 數命中次數。

> **更正（2026-09-28，5.2 容器驗收時發現）**：本檔裡「秘密的值出現在 `/work` 的
> 命中數 = 0」是**假通過**。當時的比對寫成 `for f in "${SECRETS_DIR}/*"`，而
> `/secrets` 是 `0711`（可穿越、不可列目錄）→ glob 不會展開 → 迴圈一個檔案都沒
> 掃到，所以命中數必然是 0。修好之後重測（真正掃過 4 個秘密檔、0 命中，並用
> 「把 `signing.key` 複製進 `/work`」反向驗證會報 1 並失敗）——見
> `5.2-syncer-container.md`。其餘各項（掛載、capability、docker.sock、`/Users`、
> `/secrets` 唯讀、Claude）不依賴那個迴圈，結論不變。

## 0. 前置：colima 的 DNS 與架構

- colima 2 CPU／3.9 GiB（本機沒有其他專案的容器在跑，`docker ps` 只有 10 個
  32 小時前結束的 k8s 殘留），所以**不需要**為了別人重啟。
- **DNS 故障**：VM 內的 systemd-resolved 指向失效的 IPv6 resolver，
  `docker pull` 會 `no such host`。宿主機同樣查不到（`192.168.0.1` 與 `8.8.8.8`
  本身是好的，壞的是 macOS 系統 resolver 的上游）。處置：**只改 VM 內**的
  systemd-resolved drop-in，宿主機網路設定不動：

  ```
  /etc/systemd/resolved.conf.d/aistorage-dns.conf
    [Resolve]
    DNS=8.8.8.8 1.0.0.8
    FallbackDNS=8.8.8.8
  # systemctl restart systemd-resolved
  ```

  這是 VM 內的持久設定（`colima delete` 才會消失）；`colima stop && start` 會保留。
  若 DNS 又壞，先看這個檔案在不在。
- **架構陷阱**：本機 `ubuntu:24.04` 標籤曾快取成 **amd64**，在 arm64 的 VM 裡
  讓 arm64 的 opencode 靜態執行檔報 `required file not found`。
  `resident/build.sh` 現在會帶 `--platform linux/arm64`（依 `uname -m` 判斷）。
  另外 colima **沒有 buildx**，所以 Dockerfile 不能只靠 BuildKit 的 `TARGETARCH`
  ARG；`build.sh` 用 `--build-arg` 傳入，Dockerfile 內部再以 `uname -m` 兜底。

- 只有 `/work`（可寫）與 5 個 `/secrets/<檔名>`（**全部 ro**）來自宿主機。
- `/secrets` 目錄本身是 `0711`（可穿越、不可列目錄）：容器以 Mac 的 uid 執行，
  必須能穿越才能讀到檔案；但 `ls /secrets` 會被拒絕（實測：
  `ls: cannot open directory '/secrets': Permission denied`），
  已知路徑則可直接存取。
- 掛載是 colima 的 sshfs（`fuse.sshfs`），`user_id=501,group_id=1000`。

## 5. 完整啟動流程（`--no-tui`）

`resident/run.sh boundary-1 --profile mac-opencode --model opencode/space-bunny-free --no-tui`：

1. 白名單檢查 → 掛 5 個唯讀 secret
2. `rclone-worker.conf` → `/tmp/aistorage/rclone.conf`（600，可寫）
3. 產生 `/tmp/aistorage/opencode.json`：
   `model=opencode/space-bunny-free`、
   `provider.opencode.options.apiKey={"file:/secrets/llm-opencode.key"}`
4. `opencode serve --hostname 127.0.0.1 --port 4096` 就緒，
   `GET /session` 回 `[]`（**沒有跑 LLM**，只是 serve 在服務）
5. `/work/.local/share/opencode/auth.json` **不存在** → 金鑰走檔案引用時
   opencode 不會寫出明文憑證（1.7a M4 的顧慮在真實容器裡也成立）
6. `aistorage.schema` 需要 `schemas/`，wheel 裡沒帶 → entrypoint 啟動時把
   `/opt/aistorage/schemas/*.json` 複製到 `/work/schemas`（已存在就不覆寫）
7. 同步器（5.2 還沒實作）：`No module named aistorage.syncer` →
   entrypoint 記警告後**繼續**讓容器活著（serve 不受影響）

過程中修掉三個真實環境才會遇到的問題：

- `/secrets` 是 root 的 0700 時，uid 501 連 `stat` 都做不到，entrypoint 會誤判
  「缺少必要檔案」→ 改成 0711。
- serve 剛起來時第一次 `GET /session` 可能連得上卻不回應，沒有 `--max-time` 的
  `curl` 會把整個 entrypoint 卡死（實測卡住）→ 加上 `--connect-timeout 2 --max-time 5`，
  並在 60 秒內沒就緒時明確失敗。
- `cryptography` 47+ 的 aarch64 wheel 在這個 colima VM 上會 SIGILL
  （VM 的 CPU Features 沒有 armv8.2+ 的 LSE/SHA 系列）→ image 內固定
  `cryptography>=42,<47`（46.0.3 實測可用）。這是**容器執行環境**的限制，
  Mac 上的開發環境不受影響。

## 6. 測試用的簽章金鑰

- 由 `python -m aistorage.identity keygen --profile mac-opencode` 產生到
  `~/.config/aistorage/test-keys/signing.key`（600，目錄 700）。
- **只以路徑引用**；本檔不記 key_id 以外的值，也不記私鑰內容。
- resident 用的 profile 目錄 `~/.config/aistorage/resident/mac-opencode/` 裡：
  `signing.key`（測試金鑰）、`rclone-worker.conf`、`sa-reader.json`（皆自
  `~/.config/aistorage/` 複製）、`reader.json`（`manifest_file_id` 是明確標示的
  佔位值，正式 id 要等 PM 以提交流程身分初始化 manifest 後填入）、
  `llm-opencode.key`（**明確標示的佔位值**，這次只錄能力邊界、沒有跑 LLM）。

> **更正（2026-09-28，5.4 驗收）**：這個佔位值後來被證明是**有害的**——
> `apiKey` 指向一個佔位／不存在的檔案時，opencode 連 `POST /session` 都會回 400。
> 現在 `opencode` 這個 provider 走「免金鑰」路徑（`AISTORAGE_KEYLESS_PROVIDERS`，
> 預設含 `opencode`）：沒有金鑰檔時 `resident/run.sh` 不要求它，
> `entrypoint.sh` 產生的設定會**整個移除 provider 區塊**，不留 `{file:}` 參照。
> 實測（容器內、沒有 auth.json、沒有任何金鑰檔）：`回覆 OK` 4 秒回完、
> `finish=stop`、`cost=0`。佔位值檔案已從 `resident/mac-opencode/` 移除。
> 本檔其餘紀錄（掛載、capability、docker.sock、`/Users`、`/secrets` 唯讀）不依賴這一項。

## 7. 結論

| 邊界 | 狀態 |
|---|---|
| 憑證只從白名單掛、且唯讀 | ✓ |
| 目錄裡有白名單外的檔名就拒絕啟動 | ✓（單元測試涵蓋） |
| 工作目錄每個容器一份、互不可見 | ✓ |
| 不掛 docker.sock、不加 capability、不 privileged | ✓ |
| 秘密的值不出現在 `/work` | 重測 ✓（0 命中，見 `5.2-syncer-container.md`；本檔原記的 0 是無效檢查） |
| 沒有 Claude 的憑證 | ✓（環境變數與檔案都沒有；啟動時還會主動拒絕） |
| LLM 金鑰以檔案引用提供，不寫明文 auth.json | ✓ |
| 模型與 provider 是設定值，不寫死在 image | ✓（`--model` 決定） |
