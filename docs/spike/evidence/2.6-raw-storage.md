# 2.6 原始紀錄存放機制評估：Git Blob vs. Git-Annex Object

- **執行時間**：2026-09-27 08:22 〜 15:35 UTC（總耗時約 7 小時）
- **執行環境**：Mac arm64 容器 `s26`，掛載真實 Google Drive 服務帳號（`rclone-committer-test.conf`），隔離執行於 `TEST_FOLDER_ID`
- **合成負載**：10 個 Session，模擬 200 輪增量同步（每輪隨機挑選 1〜4 個 Session 追加 1〜3 則訊息，Session 大小成長至 0.5〜3 MB），總計執行 200 次 commit & push
- **判定**：**推薦採用 Config B（Git-Annex Object）**，`annex.max-git-bundles` 設為 **10**。

---

## 一、量測目的與配置對比

評估增量成長的 JSON 原始紀錄（每次同步追加新版本）應採用何種存放策略：

| 評估配置 | 核心機制 | 預期優勢 | 潛在代價 |
|---|---|---|---|
| **Config A**<br>(Git Blob) | `annex.largefiles` 排除 `*.json`，原始紀錄存為標準 Git blob | Git pack 具備良好 delta 壓縮能力，歷史物件儲存較緊湊；clone 後所有 raw 隨歷史即時就緒（`get_raw = 0ms`）。 | 每次 consolidate 需重新打包並上傳包含全部歷史 raw 的 Git bundle，bundle 體積隨版本增長急遽膨脹。 |
| **Config B**<br>(Git-Annex Object) | `annex.largefiles=include=*.json`，原始紀錄存為 Git-Annex 外部物件 | Git bundle 僅保存 pointer 與 metadata，體積極小且增長極慢；每次 consolidate 傳輸極輕量；Git 歷史 clone 極快。 | 每個 raw 版本皆獨立存放於遠端（無 delta 壓縮），遠端檔案數較多；讀取時需經由 `git annex get` 按需下載。 |

本次實驗固定 `annex.max-git-bundles=10`，在 200 輪 push 中分別觸發約 20 次 consolidate，完整觀察生命週期與性能衰退特徵。

## 三、權衡分析 (Tradeoff Analysis)

### 1. GitHub Actions Committer 耗時與每月額度影響

依 design D1 與 1.8 提交模型（假設每月 500 次提交）：
- **Config A**：平均每輪 67.0 秒 $\times$ 500 次 = 約 **558 分鐘/月**。
- **Config B**：平均每輪 50.7 秒 $\times$ 500 次 = 約 **422 分鐘/月**。
- **效益**：Config B 每月可直接節省約 **136 分鐘** 的 Runner 時間（節省比例達 24.3%）。

### 2. Consolidate 的「滾雪球」風險 (The Snowball Risk)

- **Config A 的隱憂**：Git pack 每次 consolidate 都要重寫全部可達物件。在 200 輪實驗中，bundle 體積已經從 7.5 MB 膨脹到 10.6 MB。當系統持續運作數個月、Session 數量達到數千筆時，Git bundle 將擴大至上百 MB，導致單次 push 或 consolidate 超時失敗。
- **Config B 的優勢**：Git 只記錄 pointer，第 200 輪時 bundle 僅約 400 KB。即便系統運作 1 年，Git bundle 仍能維持在數 MB 以內，完全免疫歷史膨脹引發的 consolidate 危機。

### 3. 儲存成本 vs. 網路流量

- Config B 在 Drive 端佔用 786 MB（高於 Config A 的 174 MB），然而 Google Drive 的儲存成本極低（每年每 GB 僅約美分計）。
- 反觀每次提交流程的網路頻寬與 Runner 時間才是關鍵瓶頸。Config B 在 consolidate 時上傳僅 200~400 KB，大幅降低 GitHub Actions 對外部 Google Drive API 的流量負擔與連線中斷風險。

### 4. 讀取視圖與按需讀取 (On-Demand Reading)

- 依 design D10，讀取視圖或接續點判定通常僅需讀取「特定一個被釘住的快照」。
- 在 Config B 下，讀取端只需執行 `git clone`（16.3s）加上 `git annex get <單一 session raw>`（約 1~2s），總耗時約 18s，反而比 Config A 下載全量歷史（26.6s）更迅速且節省頻寬。

---

## 四、結論與決策建議

1. **原始紀錄存放機制推薦：採用 Config B（Git-Annex Object）**
   - 原始紀錄以 `annex.largefiles=include=*.json` 存入 Git-Annex。
   - Git 儲存庫保持輕量化，徹底杜絕歷史 bundle 隨時間無限膨脹的架構風險。
2. **`annex.max-git-bundles` 參數推薦：`10`**
   - 設為 10 可將 Drive 上同時存在的活躍 bundle 數量嚴格限制在個位數，使每次 `ls-remote` 驗證與清冊查詢控制在 4~8 秒內。
   - 由於 Config B 的 bundle 極小（平均僅 208 KB），每 10 次 push 執行一次 consolidate 的額外成本微乎其微（上傳僅耗時數秒），為最佳效能與穩定度平衡點。
