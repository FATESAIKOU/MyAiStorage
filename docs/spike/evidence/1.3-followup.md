## M2：`annex_1_3_verify.sh` 的 fail-open 修正（先做）

### 修正內容（`spike/scripts/annex_1_3_verify.sh`）

1. **依 GITMANIFEST 的順序 unbundle**（不再用 `ls -S` 依檔案大小排序）：manifest 是「有序的 bundle key 清單」，增量 bundle 有 prerequisite，順序錯就解不開；舊版用大小排序是錯的來源。`-` 前綴（待刪）的行會被跳過。
2. **任何一顆解不開 → 判「查驗無效」並回 rc=1**（不得當成無命中）：舊版把失敗 `|| true` 吞掉、只印一行，最後可能判「無命中」。現在失敗會累積 `verify_invalid=1`，直接 `exit 1`。
3. **修正一個實測抓到的假陰性**：舊版用 `git cat-file … | grep -qF`——`grep -q` 命中就提早結束，`cat-file` 收到 SIGPIPE，`set -o pipefail` 把整條管線判成失敗，於是「有命中」被誤判為「無命中」（在 `agora-m2fg` 的陽性對照中實際踩到）。改為**先落檔再 grep**（`cat-file … > objects.bin` 後 `grep -qF objects.bin`），兩處（manifest 鏈、獨立交叉檢查）都改了。
4. 新增 `bundlecheck` 子命令：只跑 bundle 段，可獨立測試（postcheck 內仍會呼叫同一段）。
5. `postcheck` 的 clone 前置加 `chmod -R u+w`（annex 物件是 0444，`rm -rf` 會 Permission denied）；clone 失敗時判「查驗無效」rc=1，不再讓後續輸出看似完成。

### 測試（負向：故意壞掉的 bundle）

在拋棄式前綴 `agora-m2fg/`（uuid `b83f474b-…`）佈置 4 顆增量 bundle，canary `SPIKE-M2-FG-CANARY-77aa` 放在最後一顆：

| 測試 | 結果 |
|---|---|
| 陽性：健康 repo、canary 在最後一顆 bundle | **rc=0，正確回報「命中 canary（manifest 鏈）」**（修好 SIGPIPE 假陰性後的結果） |
| 負向：把 manifest 鏈中第一顆 bundle 的**最後一個 byte 翻轉**後放回 remote | **rc=1，逐顆印「解不開（查驗無效）」＋「✗ …本次查驗無效（不得當成無命中）」** |

- 壞掉方式：`d[:-1] + bytes([d[-1]^0xFF])`（flip 最後一 byte，會壞掉 pack trailer 的 checksum；`git bundle verify` 會回 `inflate: data stream error`）。
- **舊版對照**：以修正前的邏輯（`ls -S` 鏈、失敗吞掉）在 4 顆 bundle 的 repo 上重建鏈，**只累積到 3 個物件、判「無命中」且 rc=0**——同一份健康資料，舊版因為順序錯而丟掉部分物件（假陰性或假綠燈的來源）。修正後同樣資料 rc=0 且正確命中。
- 原始輸出：`1.3-verify/m2-positive-canary-present.txt`、`m2-negative-corrupt-bundle.txt`（修正後）、`m2-positive.txt`／`m2-negative.txt`（`agora-m2neg/` 上的第一次版本，含 4 顆 bundle 的負向）。

**判定：pass**（fail-closed＋順序正確＋SIGPIPE 假陰性修正；負向測試證明壞 bundle 會 rc=1）。
