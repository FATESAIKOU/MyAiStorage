# 1.7b 以內容判斷有沒有新內容（冪等偵測）

- 執行時間：2026-09-26 07:30〜08:0x UTC（16:30〜17:0x JST）
- 執行者：impl3；容器 `oc17-main`（arm64）
- 判定：**pass**（含一個必須寫進同步器設計的 caveat：進行中匯出會取到「寫了一半」的內容，見第 3 節）

## 1. 沒有新內容時：位元組層完全一致

同一個 Session（`SPIKE-1.7-S1`，4 則訊息）連續匯出兩次：

```bash
$ opencode export "$SID" > E1.json   # rc=0 bytes=6438
$ opencode export "$SID" > E2.json   # rc=0 bytes=6438
$ shasum -a 256 E1.json E2.json
6cf056a7db3656fa49d86da365350dae31ffda59bb378d009e553abe9c0ca1fc  E1.json
6cf056a7db3656fa49d86da365350dae31ffda59bb378d009e553abe9c0ca1fc  E2.json
```

- **揮發欄位：無。** 以 flatten 後的 320 條葉節點路徑逐項比較：`same=141 diff=0 only_a=0 only_b=0`（腳本 `fdiff.py`，見附註）。
- 換一個**新 process**、隔幾秒再匯出（Efresh1／Efresh2，含 10 則訊息）：`cmp` 逐位元組相同 → `byte_identical=YES`。
- 即：沒有新內容時，整個 JSON 沒有匯出時間這類每次都會變的欄位；位元組雜湊即穩定判準（不需排除任何欄位）。

## 2. 有新內容時：一定偵測得到

追加第 3 則訊息後匯出 E3：`messages 4 → 6`，新增 `[4]`（user，新 `msg_0dca63cf6…`）與 `[5]`（assistant，新 `msg_0dca646e4…`）；前 4 則的 id 與內容雜湊逐一相同。

- 訊息層比較法（同步器可用）：對 `messages[].info.id` 序列＋每則 parts 的內容雜湊做比對；未變時前綴一致、有變時尾端多出新訊息。
- 位元組層也直接不同（6438 → 9113 bytes）。

## 3. 進行中匯出（與 1.7c M5a 共用樣本）：冪等判準的 caveat

對「一邊生成、一邊匯出」的樣本（Ej-*、Ei-*、Ex-*、Ey-*）比對：

- 每次匯出都是**合法 JSON**、rc=0，DB 沒有鎖（同一顆 sqlite 另一個 process 可讀）。
- 但 assistant 訊息在完成前，**匯出的 parts 可能已經含寫到一半的 text**：`Ey` 樣本出現 `last=assistant completed=False text_len=8306 text_has_end=True`（text part 有 `time.end` 但訊息 `time.completed` 缺席）；`Ex` 樣本第 4 次抽樣即為此形狀。也有樣本（Ej-2）是 `text_len=0, time.start 有、end 無`。
- 因此「以內容雜湊判斷有沒有新內容」仍然有效（寫到一半的內容就是一種新版內容），但同步器不可把這種**未完成**快照當成穩定的 Session 尾端；同一則訊息的內容還會再長大（part 的 `time.end` 也可能已出現）。
- 建議同步器判準（給 D4／5.2）：訊息層雜湊仍可比對；另以「最後一則 assistant 是否 `time.completed` 存在」標記快照是否落在生成中，生成中的快照仍上傳（內容不遺失），但 sidecar 可標記 `in_progress`（此欄位屬 2.2 的格式決定，回報 PM）。

## 4. 正規化規則（結論）

1. 不需要排除欄位——未變時位元組完全一致。
2. 有變時以 `messages[].info.id` 序列＋parts 內容雜湊定位新訊息（訊息 id 穩定，見 1.7c）。
3. 生成中的最後一則 assistant 另以 `info.time.completed` 缺席判定，不可當穩定尾端。

- `fdiff.py`：flatten JSON 後逐路徑比對，輸出 `STATS same= diff= only_a= only_b=`。
