## 1. Git-remote-annex remote 的建法與關鍵發現

remote 建法（`annex_repo_init.sh`）：

```
git annex initremote drive type=rclone encryption=none rcloneremotename=gdrive rcloneprefix=agora-basic autoenable=true --with-url
```

- `type=rclone`（不是舊教學的 `type=external externaltype=rclone-builtin`；後者要 symlink，且 10.20240430 以後已內建）。實測 `git annex initremote tmprem type=external --whatelse` 只列 `externaltype`，而 `rclone gitannex -h` 說明新語法。
- `encryption=none`、**chunking: none**（`annex info` 確認）→ 符合 D5「依 annex key 直接取物件」的前提。
- remote 參數記在 git-annex branch 的 `remote.log`：`type=rclone rcloneremotename=gdrive rcloneprefix=agora-basic encryption=none`。

**關鍵發現 1（URL 形狀）**：`git push drive` 印出的「Full remote url」與 `git config remote.drive.url`（`annex::`）**都缺 `rcloneremotename`／`rcloneprefix`**，直接用會失敗：

```
error: external special remote error: failed to get configs: did not receive a non-empty config value for "rcloneremotename"
```

全新 clone 必須用完整 URL（`annex_repo_init.sh` 會由 uuid＋參數組出並寫進 `<repo>.url`）：

```
annex::<uuid>?encryption=none&type=rclone&rcloneremotename=gdrive&rcloneprefix=agora-basic
```

**關鍵發現 2（clone 後要 init）**：`git clone annex::…` 出來的 repo，`git annex get` 前要先 `git annex init`（否則 `git-annex: First run: git annex init`）。1.5／同步器要照這個流程。

**關鍵發現 3（GITMANIFEST 的 id 不穩定）**：每次 push 後 GITMANIFEST 的 **file id 會變**（刪掉重建，不是原地更新）：

| 時點 | file id | modified |
|---|---|---|
| push 前 | `1DJ-IEb0iJHMseposJ-wUHCbvxSn8yDec` | 08:36:56Z |
| 小 commit + push 後 | `1fduyfS3CTIWZt_izN18L3Xb9fUbsUV_k` | 08:38:58Z |

→ **manifest 預檢不能用 file id 比對**，要用**內容指紋**（本項用 rclone 取 GITMANIFEST／.bak 的 sha256）。

## 3. arm64 容器：push 中斷後恢復（pass，有真中斷證據）

完整輸出：`1.2-annex-interrupt-arm64.log`、`1.2-interrupt-verify.log`。

- 先同步（`git fetch drive main git-annex` → `git rebase drive/main`），再做一顆 commit（3×4 MiB annex 物件）。
- push 用 `timeout -s KILL 3` **真的 SIGKILL**：

```
/work/annex_1_2_core.sh: line 20:   207 Killed     timeout -s KILL 3 git push drive main git-annex
timeout rc=137（137 = SIGKILL，代表真的中斷了）
```

- 中斷後 remote 檔案數 12（含 GITMANIFEST／.bak／3 顆舊 bundle／6 顆 annex 物件，部分上傳痕跡）；remote main 仍是中斷前的 `a555e5c`。
- **重新 push 時出現非 fast-forward**（hint: use 'git pull' before pushing again）——因為前一輪在 clone 內做的 revert 已把 remote main 往前推，原 repo 沒同步。以 `git fetch` + `git rebase drive/main` 後重推成功（`aff464c..ebdca4d main`）。
- **全新 clone（clone3）**：`HEAD=ebdca4d big files for interrupt test`，`git annex get big-{1,2,3}` 三個都與原始檔 `cmp` 一致（見 `1.2-interrupt-verify.log` 的 3/3）→ **中斷後已 commit 的內容沒有遺失**。

## 4. manifest 預檢：正向放行、負向中止（pass）

- **正向**（見 §2）：snapshot 後立即 check → PASS。量測 **`預檢讀取結束 → push 完成、manifest 寫入完成` 的窗口**：

| 量測 | arm64 容器 |
|---|---|
| 預檢讀取（2 個 manifest 物件的 sha256） | 6.9 s |
| **未保護窗口（預檢完→push 完）** | **22.6 s** |

  （另一個 `other-writer` 情境也量到 28.0 s 的重推；Drive 每秒約 2 檔 + annex bundle 上傳是主要成本。）

- **負向**：先在同一 repo 建第二個 clone `other-writer` 當「另一個寫入者」並真的 push（manifest 改變），再在原本的 clone 執行預檢：

```
負向預檢 rc=3（必須是 3）
manifest_precheck: CHANGED（遠端 manifest 與快照不同）——中止 push
  6d5512e8…  GITMANIFEST--915a333b-…
  ---
  2bb82fb0…  GITMANIFEST--915a333b-…
```

→ **預檢能阻止被覆蓋（pass）**。注意：預檢的保護窗口是「預檢讀完到 push 寫完」的 **~22 秒級**，不是零；D2 的「管理與提交錯開」在 1.6 的結論出來前，這條是主要防線（design D2 已如此設計）。

## 5. amd64 runner（pass）

- 安裝：與 `spike/env/Dockerfile` **同一種安裝法與同一組版本＋sha256**（git-annex standalone tarball amd64 `a3c9d10e…`、rclone 1.75.1 zip `982b5aa7…`）。

- **clone（從零、無快取）**：12.4 s / 13.7 s（兩次 run）；`commit 數：20`；`git annex get` 內容 3.7〜13.9 s；`big-{1,2,3}.bin` 的 sha256 與 arm64 容器**逐位元一致**（`2fabae76…`／`01f5d8ac…`／`36344abc…`）。
- **push**：14.5 s（第二次 run 含實際 push 成功）；由 arm64 容器全新 clone 驗證 runner 的 `runner-push.txt` 與 commit `738e280` 確實在 Drive 上。

### runner 上發現的兩個坑（都已修，留在 workflow）

1. **`git clone` 不會自動 checkout**：runner 的 git 較新，`git clone annex::…` 後 `warning: remote HEAD refers to nonexistent ref, unable to checkout`，建出空的 `master`，後續 `git log` fatal。→ 改成 `git clone -b main …`。
2. **push 靜默失敗**：第一次 `commit-push` run 回報成功、`Everything up-to-date`、exit 0，但 commit 沒有上 Drive（少了 `git-annex` ref 一起推；`git-remote-annex` 回報 `warning: helper reported unexpected status of push` 卻不影響 exit code）。→ workflow 改成 `git push origin main git-annex`，並在 push 後用 `git ls-remote` **驗證 remote main == local HEAD**，不符就 `::error` 失敗（防假綠燈）。第二次 run `local HEAD=738e280… remote main=738e280…`。

## 6. 判定

| 子項 | 判定 | 依據 |
|---|---|---|
| arm64 clone／commit／push／log／diff／revert＋新 clone 雜湊一致 | **pass** | §2 |
| push 中斷後恢復、不遺失已 commit 內容（有真中斷） | **pass** | §3 |
| manifest 預檢正向放行 | **pass** | §2、§4 |
| manifest 預檢負向中止（真的改變 manifest） | **pass** | §4 |
| manifest 更新方式有記錄（**id 會變**，需用內容指紋） | **pass** | §1 關鍵發現 3 |
| 預檢窗口時間有數字（~22 s，另記 28 s） | **pass** | §4 |
| amd64 runner clone／get／push＋雜湊一致 | **pass** | §5 |
| 兩邊安裝方式與版本記錄 | **pass** | §5 |

**整體：pass。** 供 1.9 的注意事項：
- 預檢必須用**內容指紋**（GITMANIFEST file id 每次 push 都變）；窗口 ~22 s（Drive 的檔案速率），非零但可接受（1.6 的 workflow 開關結論出來前，這是主要防線）。
- clone 後要 `git annex init`；全新 clone 要用**完整 URL**（含 `rcloneremotename`／`rcloneprefix`），不能只用 push 印出的完整 URL。
- runner 上 push 必須同時推 `main` 與 `git-annex`，且要驗證 remote head（會有 exit 0 的靜默失敗）。
- 1.2 的 arm64 容器掛了 committer conf（一次性驗證容器），住民容器版本由 5.1 驗。
