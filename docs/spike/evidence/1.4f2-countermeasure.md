## 判定

| 項目 | 判定 |
|---|---|
| 清冊清掃＋tip 釘選能否阻止「無聲替換歷史」 | **能**：偽造一律被「釘選不符或 clone 失敗」擋下（exit 2、不 push），三種順序、四種窗口都驗過 |
| 清掃後恢復 | **能**：一致偽造對、純同名 DoS、上一層同名資料夾三種情境清掃後 clone 都回到釘選值 |
| 能力是否消失 | **否**：C 仍能把檔案寫進 repo 資料夾（與 1.4e／1.4f 相同），只是從「無聲」變成「偵測得到的 DoS」 |
| 與 review 對策表對應 | 對策 2＋3 可行；補上 H6 的上一層掃描後**沒有發現能繞過的路徑** |

**限制與代價（照 review 對策表的預期，實測證實）**：
1. **DoS 仍存在**：住民能持續注入使 clone 失敗；恢復要等下一輪清掃。與 REQ「禁止的能力要做成根本不存在」的原則衝突——需要使用者對「偵測得到的 DoS 可接受」明示接受。
2. **清掃與 clone 之間仍有窗口**：本補測的核對（clone 後驗 HEAD）會中止，但**該輪提交就是失敗的**；預檢（1.2 M8）與清掃都只是把窗口縮小。
3. **上一層同名資料夾必須一併清**（H6）；實作時要列入提交流程每一輪的步驟。
4. **隔離而非刪除**：被移出的檔還在專用帳號的 Drive 裡（本測試保留作證）；正式設計要決定隔離物的保存期限與永久刪除方式（與 1.3 的抹除範圍一起）。
5. 本對策**只解決 repo 的無聲替換**；收件匣偽造（1.4d／1.4i、H3）與配額（M3）不受影響——review 建議的對策 1 或 7 是另一條線。
