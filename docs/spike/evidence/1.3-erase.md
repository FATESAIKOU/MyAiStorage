## 一、canary 佈置與「抹除前找得到」（防假陰性）

canary 放在三處（`setup`）：

1. `erase-canary.txt` 的 v1 commit（歷史）與 v2（現行版本）；
2. **annex 物件**：`big-annex.bin`（192,053 bytes，`annex.largefiles=largerthan=100kb` 進 annex）內容含 canary；
3. remote（Drive）上的 GITBUNDLE／GITMANIFEST 與 annex 物件（`SHA256E-s192053--cb5b33cc…`）。

`precheck`（`annex_1_3_verify.sh`）逐處證明**抹除前都找得到**：工作樹 grep、`git grep HEAD`、`git log --all -S`、`git rev-list --all --objects`、本機 annex 物件、**remote annex 物件（取回後 grep）**全數命中。→ 查驗方法有效，後面的「找不到」不是假綠燈。

## 二、抹除流程（實際採用的手法）

```
A) git annex drop --force big-annex.bin               # 本地副本
   git annex drop --force --from=drive big-annex.bin  # remote 副本（whereis 變 0 copies）
B) git annex forget --force
B2) chmod -R u+w .git/annex/objects && rm -rf .git/annex/objects
   # filter-repo 不會碰 annex 物件；留著會在重建時被重新上傳（實測踩到，見「四」）
C) git update-ref -d refs/annex/last-index   # git-annex 的索引樹會保留舊 blob（實測踩到）
   git filter-repo --force --replace-text <canary→REDACTED> --invert-paths \
       --path erase-canary.txt --path big-annex.bin
   git update-ref -d refs/annex/last-index; git reflog expire --expire=now --all; git gc --prune=now
   （若 filter-repo 把 main 清空，則重建空 main）
D) 本機掃描：git log -S／rev-list／cat-file --batch-all-objects／annex 目錄 全部 0 命中
E) git push --force drive main git-annex
F) （必要時）**刪檔重建**：永久刪除 `agora-erase/`（files.delete，204），再 `git push` 重建
```

## 四、實測發現（決定了手法）

1. **`git push --force` 之後舊 GITBUNDLE 仍留在 remote 上**（git-remote-annex 的設計：re-upload 不會刪舊 GITBUNDLE 物件；官方 man 已寫明「re-upload does not delete old GITBUNDLE objects」）。實測每次 force push 後都還能在舊 bundle 裡還原出 canary（`8ce8ad99`／`7fc5b66c`／`a4935c91` 三組各自都印出「>>> 此群組含 canary：可從垃圾桶還原」）。→ **只覆寫（force push）不夠**。
2. **`refs/annex/last-index` 會保留舊 blob**：filter-repo 不處理這個 annex 內部 ref，第一次抹除後本機仍留有 2 個 canary blob（`831b555d…`、`9ef9b282…`）。→ 抹除流程必須 `git update-ref -d refs/annex/last-index`（本檔流程已含）。
3. **filter-repo 不會碰 `.git/annex/objects`**：留著的 annex 物件會在重建時被**重新上傳**（第一次重建後 remote 又出現含 canary 的 `SHA256E-s192053--cb5b33cc…`）。→ 必須先 `chmod -R u+w .git/annex/objects && rm -rf`（annex 物件是 0444 唯讀，直接 rm 會 `Permission denied`）。
4. **`git gc --prune=now` 要在最後一次改寫之後跑**：filter-repo 留下的 dangling blob（`831b555d…`、`9ef9b282…`）若沒 prune 掉，本地掃描仍會命中（實測）。
5. **刪除 ≠ 永久刪除**：`rclone deletefile`／`purge` 預設丟垃圾桶（1.1 已觀察，1.3 再次確認）；Drive API 的 `files.delete` 才是永久刪除。
6. **需要刪檔重建**：因為 (1)，最終以「永久刪除 `agora-erase/`（204）＋從乾淨的本機 repo 重推」完成；重推後 remote 只有 1 個 GITBUNDLE，且 unbundle 後不含 canary。

## 六、判定

**pass（採用「刪檔重建＋永久刪除」路徑）**，但附帶重要 caveat：

- a〜e 全部找不到 canary（內容與檔名皆無），f 有紀錄。
- **手法是「刪檔重建」，不是「覆寫」**：`git push --force` 無法清掉舊 GITBUNDLE；必須永久刪除 remote 上的舊物件（或整個 prefix 資料夾）後重建。這對 6.1 抹除腳本是硬需求，也證實 design Risks「抹除後內容仍在 Drive revision 與垃圾桶」為真。
- 抹除會**破壞 annex 物件的所有副本**（drop --force 沒有其他副本）；正式環境若靠 clone 當非正式備份，抹除後那些 clone 仍是擴散點（design D2 已列，6.1 要提醒）。
- 抹除後 repo 變成空的 `erase: repo rebuilt empty after data removal`（本案 canary 檔就是全部內容；正式環境會有其他內容）。
- 每次抹除的**成本**：本案例（6 物件、1 個 small bundle）約數十秒；`filter-repo` 對 10 commits 0.4 s、gc 1.7 s；Drive 刪除與重推受檔案速率限制。

**no-go 檢查**：canary 最終在目前版本、git 歷史、bundle、Drive revisions、垃圾桶全都找不到 → 未觸發「抹除不乾淨」的 no-go。但因手法必然是刪檔重建，**1.9 需把「抹除＝刪檔重建」寫進 design（spec「抹除」的實作註記）**。
