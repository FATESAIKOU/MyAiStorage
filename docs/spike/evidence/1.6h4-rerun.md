# 1.6 H4：住民能 rerun 舊 run——舊 workflow 定義＋舊 commit，用當下的 secrets

- 執行時間：2026-09-26 11:45〜11:55 UTC（20:45〜20:55 JST）
- 執行者：impl3
- repo：`FATESAIKOU/aistorage-spike`（測試 repo）
- 規則：PAT（`gh-pat-actions.txt`）只以檔案路徑引用、不進 argv／prompt／log；推 commit 用**我自己的 gh 登入身分**（`FATESAIKOU`，非 PAT）；證據只記 run id／sha／布林值

## 要回答的問題

1. 住民的 PAT 能不能 rerun 一個舊的 run？
2. rerun 的 run 跑的是**當初那次 run 的 commit 與 workflow 定義**（而不是現在的 main），且用**當下的 secrets**？
3. 若 workflow 加上「`github.sha` 必須等於 `main` HEAD，否則立刻結束」的檢查，能不能擋掉「rerun 修補前的舊 run」？

## 1. rerun 舊 run：確實跑舊 commit、舊定義（H4 的風險成立）

對象：`spike-empty-check` 的舊 run `36227666548`（headSha `8c514c50`，2026-09-26 07:43），當時 main 已前進到 `af4d5a67`（後續又到 `fc446c76`）。

```bash
$ GH_TOKEN="$(cat ~/.config/aistorage-spike/gh-pat-actions.txt)" gh run rerun 36227666548 --repo FATESAIKOU/aistorage-spike
# 接受；attempt 2 開始執行
$ gh run view 36227666548 --json status,conclusion,attempt
{"attempt":2,"conclusion":"success","status":"completed"}
```

rerun 的 log（checkout 步驟）證明它拿的是**舊 sha**：

```
[command]/usr/bin/git -c protocol.version=2 fetch --no-tags --prune --no-recurse-submodules --depth=1 \
  origin +8c514c50601399eb91991add90d7d266935b7584:refs/remotes/origin/main
 * [new ref]  8c514c50601399eb91991add90d7d266935b7584 -> origin/main
[command]/usr/bin/git log -1 --format=%H
8c514c50601399eb91991add90d7d266935b7584
```

- 當時 main HEAD 是 `af4d5a67`／`fc446c76`，rerun 卻 checkout `8c514c50`。**rerun 固定用「原先 run 的 commit」**（與 GitHub 文件一致：rerun 用原始 run 的 `GITHUB_SHA` 與該次 run 的 workflow 定義），secrets 則取自**當下**的 repo secrets。
- 這個 run 之所以成功，是因為它的定義（`8c514c50` 版）本來就是無害的檔案清單探測；但同一機制套在「修補前的提交流程 workflow」上，就是「用舊的、有漏洞的程式碼，配當下的 `RCLONE_CONF`」——H4 的風險成立。

## 2. 加檢查的證明：用一個測試 workflow 的 v1／v2b

在測試 repo 新增 `h4-sha-guard-test.yml`（**用我自己的 gh 登入身分 push**，非 PAT）：

- **v1（`fc446c76`，無檢查）**：觸發一次 → run `36240053095`（success）。
- **v2b（`8cf6d05`，加檢查）**：檢查內容＝`gh api repos/$GITHUB_REPOSITORY/commits/main --jq .sha`，與 `$GITHUB_SHA` 不符就 `::error` ＋ `exit 1`。觸發一次 → run `36240108102`（success；此時 sha 與 main HEAD 相同）。

### 2a. 舊 run（v1，無檢查）被 rerun：照跑舊定義，檢查不存在

```bash
$ GH_TOKEN="$(cat …gh-pat-actions.txt)" gh run rerun 36240053095 --repo …   # v1 舊 run
$ gh run view 36240053095 --json attempt,conclusion                           # attempt=2, success
# log:
workflow_version=v1-no-guard
GITHUB_SHA=fc446c764365ff3e9f78613864edc09ce49f88c4
RUN_ID=36240053095 ATTEMPT=2
```

→ rerun 舊 run 時，**跑的是舊的（無檢查的）workflow 定義**；檢查無法追溯保護修補前產生的 run。

### 2b. 加了檢查之後產生的 run 被 rerun：檢查有效（通過與攔截各一次）

| 情境 | 操作 | sha | main HEAD 當時 | 結果 |
|---|---|---|---|---|
| 一致 | rerun v2b run `36240108102`（attempt 2） | `8cf6d05` | `8cf6d05` | **success**（「SHA 檢查通過」） |
| 不一致 | 先推一個空 commit 讓 main 前進到 `1018d04`，再 rerun 同一個 v2b run（attempt 4） | `8cf6d05` | `1018d04` | **failure**，log：`::error::github.sha(8cf6d05…) != main HEAD(1018d04…)：這個 run 用的不是 main 最新版——立刻結束` |

→ 檢查在「有帶檢查的版本之後產生的 run」上有效：`github.sha` 與 main HEAD 不一致時確實立刻失敗（attempt 4 於第一顆 step 即結束）。

## 3. 結論與邊界（重要）

- **H4 風險成立**：住民 PAT 能 rerun 舊 run；rerun 用**舊 commit 的 workflow 定義**與**當下的 secrets**。若「修補前的 workflow」有安全漏洞，rerun 就等於用舊程式碼取得現在的秘密。
- **`github.sha == main HEAD` 檢查的邊界**：
  - 它**保護不了修補前產生的舊 run**（2a 實證：rerun 舊 run 跑舊定義，根本沒有這道檢查）。
  - 它**保護得了修補後（帶檢查版本）產生的 run**（2b 實證：main 前進後 rerun 會被攔截、立刻失敗）。
  - 因此 D2 的規則要寫成：**修補 workflow 安全問題之後，必須把舊的 run 刪掉（PAT 可刪，1.6 已證）並輪替 `RCLONE_CONF`**；只有 `github.sha` 檢查不足以關掉已存在的舊 run。
- 註：本次只證明「檢查會讓不一致的 run 立刻結束」；沒有證明「所有舊 run 都會被檢查擋下」（它們跑的是舊定義，必然不會）。這是結論的邊界。
