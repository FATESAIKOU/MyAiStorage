8. **對策檢查**：git-remote-annex 10.20260717 的 man page 無任何 id 定位／簽章選項；manifest 只是純文字指標檔（內容為 bundle 檔名），bundle 只以「檔名內嵌 sha256」驗完整性——**攻擊者自己算得出**。無「固定 file id」「manifest 綁定」機制可用。

**對策檢查與替代方案（找不到可行對策）**：
- **以 id 定位的路徑**：D5 只讓「讀取視圖的 manifest」以固定 id 定位；Agora repo 的 GITMANIFEST／GITBUNDLE 由 git-remote-annex 以**檔名**存取，helper 沒有可設定的 id 選項。要修得自己換掉 helper 的名稱解析（等於換掉 ADR 0005 的選型），不是設定能解的。
- **加密（rclone crypt／annex encryption）—未實測**：推測能讓 C 無法造出「內容與名稱相符」的偽造物件，但 (a) 仍擋不住同名注入造成的 DoS（clone 直接失敗）、(b) 與 D5「依 annex key 直接取物件」的前提衝突——test-plan 明文要求 `encryption=none`、不開 chunk。若要靠加密當對策，需要另外的技術驗證與設計變更，不能算既有對策。
- **manifest 預檢（1.2 M8）**：只有在「C 在 committer clone 之後才注入」時能偵測（manifest 指紋不符→中止）；C 只要在**下一次 clone 之前**先佈置好一致偽造對，clone 拿到的就是偽造歷史、預檢也會放行。**攻擊是被動的、不需要競速窗口。**
- **同名偵測**：rclone 對同名不報錯（`lsjson` 正常回多筆、`lsf` 選一個），沒有「發現同名就中止」的開關。
- 結論：在「git-remote-annex＋rclone＋Drive、encryption=none」的前提下，**找不到能阻止「寫入 repo 資料夾」的對策**；唯一能想到的修法是改成全程以 file id／雜湊定位的自製 remote helper，那已經是重新選型。

**判定**：C **建得進去且找不到對策**（可 DoS、也可無聲替換整個歷史）→ **FAIL，觸發 test-plan 第 1 節 no-go 條件 1 與 design Risks 原文**。

> **補測（2026-09-26，使用者核准）**：review-1.4 指出 no-go 條件的「對策」範圍太窄後，impl2 補測了**對策 A＝清冊清掃＋tip 釘選**。結果：對策可行——無聲替換一律被擋下、可恢復；但 C **寫得進去的能力本身沒有消失**（從無聲變成偵測得到的 DoS），且需加做「上一層同名資料夾」清掃（H6）。詳見 `docs/spike/evidence/1.4f2-countermeasure.md`；1.9 彙整時以該檔的判定為準（本節「找不到對策」僅指 rclone／git-remote-annex 那一側）。

## 1.4h 同名檔在以上各處的行為（含上一層前綴） — **FAIL（存在以檔名定位且可被同名混淆的路徑）**

- Drive 允許同名；**同名 create 是新增重複檔（每次新的 file id），不是覆寫**。實測 readview 內連建 2 個假 `manifest.json`：committer／SA 依名稱查得 3 筆（2 假＋1 真），C 只看到自己那 2 筆；真檔不受影響（SA 依 id 讀 sha256 `4d9b…483` 不變）。
- 一般列舉：owner／committer 視角的 `find-name` 回傳全部同名檔（真假並存），**creator 視角（C）只看到自己那筆**；同 project 的其他 client（A／B）看到的是他們自己的檔案集（例如 B 看不到 C 注入的 `b-inbox.txt`，committer 看得到 2 筆同名）。
- 以 file id 定位時行為明確、不受同名影響（1.4g／1.4i 已證）。
- **以檔名定位（rclone／git-remote-annex）會被同名混淆**：同名檔在 repo 前綴內 → clone 失敗；**一致偽造對 → clone 拿到偽造歷史**；上一層同名資料夾 → rclone 解析到錯的資料夾、clone 失敗或拿到偽造歷史（1.4f 第 4〜7 點）。

**判定**：FAIL——存在以檔名定位且可被同名混淆的路徑（就是 git-remote-annex＋rclone 那條）。依 1.9 表為「需要改設計」；但 1.4f 已是 no-go。

   - 註：SA 只能讀被分享的範圍；A 的收件匣在根目錄、未分享給 SA，SA 對它 404——這是預期（收件匣不在讀取路徑上）。manifest 測試放在 `SPIKE_FOLDER_ID` 下才成立。

**判定**：bootstrap、登記、manifest 原地更新與延遲數字 **PASS**；步驟 4 的 C 注入 **FAIL**（收件匣隔離在跨 project 下不成立）。依 test-plan 1.4i 的條文判定為：設計面可行、但「收件匣只有自己寫得進去」的安全前提不成立。

## 共同判定與 no-go

1. **隔離單位＝GCP project**：同 project（A/B/committer，含跨 client、含 A 對 committer 的資料夾）**完全不隔離**（可見、可改、可刪、可授權）；跨 project（C）對**既有檔案的讀／改／刪／授權全部被拒**（404／403＋reason）。
2. **但隔離不涵蓋「建檔」**：跨 project 的 `drive.file` client 只要知道資料夾 id，就能在該資料夾裡建立檔案（含同名檔）——1.4d（別的 profile 的資料夾）、1.4e（committer 的 `SPIKE_FOLDER_ID`）、1.4f（repo 前綴與其上一層）、1.4i（別的 profile 的收件匣）都成立。
3. **1.4f 觸發 design 明定的 no-go**：C 能在 repo 資料夾建檔，且 rclone／git-remote-annex 側找不到對策——可 DoS（同名注入讓 clone 失敗）也可**無聲替換整個歷史**（一致偽造對通過 sha256 名稱檢查）。`每個 profile 各開 GCP project` 只解決 client 之間的可見性，解決不了這一條（design Risks 已預言）。
4. 依 test-plan 第 1 節第 2 條，1.4d／1.4e／1.4f「能寫進 committer／別的 profile 的資料夾」亦直接命中；**結論導向 no-go**，不是 caveat。
5. D5 的「以固定 file id 定位讀取路徑」在讀取視圖上成立（1.4g／1.4i），但**擋不住寫入端在 repo 的注入**。
