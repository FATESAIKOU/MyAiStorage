### 1.2 3.1-3：先卡住，再驗成——兩個必須一起講的教訓

**第一輪的 dead end（`833dfd0` 上的 36686407460）**：`gh run rerun` 會沿用**原本那個
run 的 `head_sha`** 與同一個 `databaseId`（`run_attempt` 加一）。所以 rerun `833dfd0` 上的
那個 run，用的是 **`833dfd0` 那一版的 `committer.yml`**——而那一版正是含 B1 壞 SHA 的：

```
commit  Set up job  …  Getting action download info
##[error]Unable to resolve action `astral-sh/setup-uv@16b49045b85040e34c9f13674686b24a3500854d`
```

該 run 的步驟清單只有 `['Set up job']`（failure）——**根本沒有 `guard` 這個步驟**。
它不算通過，但**也不是** guard 有問題：它只是走不到 guard。這兩種「沒擋到」必須分開，
否則會把一個壞掉的舊 workflow 檔誤讀成防護失效。harness 會自己診斷（`diagnose_pins_at()`）：

```
rerun（attempt 2→3）沒有 guard 這個步驟：['Set up job']。rerun 用的是 sha 833dfd0 上
的 workflow 檔，那一版本身跑不起來（死在 job setup），guard 根本沒跑到——這不算通過，
也不代表 guard 有問題。診斷：833dfd0… 上的 workflow 檔釘了 1 個解析不了的 action SHA：
astral-sh/setup-uv@16b49045b850…。要驗 sha 檢查，請改 rerun 一個 workflow 檔是好的舊 run。
```

**要真的驗到 sha 檢查，需要同時滿足三個條件**：

1. run 是在 **`main`** 上 dispatch 的（否則 `GITHUB_REF` 先擋，測到的是 ref 檢查不是 sha 檢查）；
2. 那個 sha 上的 **workflow 檔是好的**（`833dfd0` 不符合）；
3. 那個 sha **已經不是** 遠端 `main` HEAD。

PR #2 合併後 `main` 停在 `41b2d57`，而當時在 `main` 上產生的 run 也都是 `41b2d57`（== HEAD），
條件 3 不成立。第二輪因此留下三個**符合條件 1、2** 的 run 等著。PR #3 合併、`main` 前進到
`351e273` 之後，條件 3 成立，一個指令收掉：

```bash

# PASS  rerun（attempt 1→2）停留在舊 sha 41b2d57（遠端 main 已經是 351e273），
#       guard 拒絕（failure），後面 0 個步驟被執行
```

   有斷言它的形狀（`test_guard_sha_check_is_reachable_in_the_yaml` 釘住三段的順序），
   但「順序對」不等於「會在真的情況下觸發」。

### 1.3 concurrency 的細節（值得記一筆）

`concurrency: {group: committer-agora, cancel-in-progress: false}`（`committer.yml:8-10`）
的實測行為，比單元測試假設的更細：

| 時序 | 觀察 |
|---|---|
| t=0 觸發 run A | A `in_progress` |
| t=2s 觸發 run B | B `queued` → `pending`（**沒有**同時跑 ✓） |
| t=4s 觸發 run C（非 main 分支） | C 進同一個 group；**B 被 `cancelled`** |

`cancel-in-progress: false` 只保住**已經在執行中**的那一輪；還在 `pending` 的會被**後來
到達的 run 取消**。這是 GitHub concurrency 的既有行為，不是設定寫錯。

對提交流程本身無害（下一輪會撈到同一批收件匣項目，3.4 的內容雜湊去重也擋得住），但兩件事
要記得：

1. 排程與手動 `同步並提交`（5.3）撞在一起時，手動那一輪可能連 started 都沒開始就沒了。
   5.3 的逾時訊息要能分辨「被取消」和「逾時」。
2. 6.5 的管理操作期間，住民的 dispatch 可能被管理操作期間的 dispatch 取消掉。

### 1.4 假綠燈檢查

- **3.1-1 的「成功」是真的成功**，不是因為失敗發生在預期的地方就算過。harness 的
  `check_guard_main` 斷言的是兩件事：guard 自己的 `conclusion == "success"`，**而且**
  第一個失敗步驟排在 guard **之後**。第一輪的 B1 之所以被抓到，就是因為它讓第一個失敗
  步驟是 `Set up job`（在 guard 之前），判定為 fail。
- **3.1-2 的「0 個步驟被執行」有兩層**，兩層都成立才算過：① guard 的 `conclusion` 不是
  success；② 扣掉 GitHub 合成的 `Post …`／`Complete job` 之後，**沒有任何 conclusion 不是
  skipped 的 workflow 步驟**。只查 ① 會漏掉「guard 放行但後面照跑」；只查 ② 而沒扣掉
  合成步驟會產生假警報（見 §5.2）。
- **3.1-4 的 `Metadata: read` 不是漏網之魚**：GitHub 給每個 run 固定這個權限，workflow 檔裡
  寫了也去不掉。判定時要把它當成「隱含值」而不是額外授權。
- **3.1-3 第一輪「沒擋到」的原因是 rerun 走的是 `833dfd0` 那個跑不起來的 workflow 檔，
  不是 guard 放行。** 兩者的差別可以從步驟清單看出來：前者只有 `['Set up job']`
  （**根本沒有 guard 步驟**），後者有 `guard: failure` 加一整排 `skipped`。
  `check_rerun` 會明確分辨並印出診斷。第三輪換成 workflow 檔是好的 `41b2d57` 之後就 pass。
- **3.1-5 的驗證有效**：concurrency 由 Actions 的排程器在 job 建立**之前**執行，所以不受
  B1 那個 action 解析錯誤影響——第一輪在 B1 未修時就已經量到了。
- **guard 的兩道檢查必須分開算。** 3.1-2 與 3.1-3 表面上都是「guard 失敗」，但一個是
  ref 檢查、一個是 sha 檢查。`check_guard_branch` 與 `check_rerun` 各自斷言對應的那一道，
  而且 `check_rerun` 會先確認 `headBranch` 真的是 `main`——否則測到的其實是 ref 檢查
  （`GITHUB_REF` 的判斷在 sha 之前），會變成假通過。

### 2.2 B2 的修正細節（`workflow_enabled`）

```python
# 修正前：gh workflow view 沒有 --json，實測 rc=1 "unknown flag: --json"
self._run("workflow", "view", workflow, "--json", "state", "--jq", ".state")

# 修正後
self._run("workflow", "list", "--all", "--json", "path,state", "--limit", "200")
```

兩個坑：

1. `gh workflow view` 沒有 `--json`。四個單元測試的 fake 都寫成
   `if cmd[1:4] == ["workflow", "view"]`，所以**單元測試永遠抓不到**。
   `lock.py:251` 原本的 docstring 寫「整合測試驗證 gh 語法」，但
   `tests/integration/test_admin_stagger_integration.py:70` 的 `_FakeGh` 也是假的——
   兩層都沒碰到真的 `gh`。

## 5. `scripts/check_workflow_guards.py`

把「單元測試證明不了、必須在真的 GitHub 上跑」的那些檢查收在一處。

| 檢查 | 驗什麼 | 最終結果 |
|---|---|---|
| `pins` | workflow 檔裡每個 `uses: owner/repo@<40 hex>` 都用 `gh api repos/…/commits/<sha>` 查得到 | **pass**（2/2） |
| `guard-main` | 在 main 上 dispatch：guard 必須放行，且**第一個失敗步驟在 guard 之後** | **pass**（3.1-1） |
| `guard-branch` | 從非 main 分支 dispatch：guard 必須拒絕，且後面 **0** 個 workflow 步驟被執行 | **pass**（3.1-2，6 個 skipped） |
| `permissions` | 從 log 的 `GITHUB_TOKEN Permissions` 節解析，比對「workflow 宣告的 ＋ 隱含的」 | **pass**（`contents`＋`metadata`） |
| `concurrency` | 連續兩次 dispatch，斷言不會有兩個 `in_progress` | pass（第一輪） |
| `inputs` | `-f anything=x` 必須被拒絕**且不產生 run** | pass（第一輪） |
| `rerun` | 帶 `--rerun <id>`：舊 sha 上 rerun，guard 必須**因為 sha 對不上**拒絕（並先確認 `headBranch` 是 `main`，否則測到的是 ref 檢查） | **pass**（第三輪，3.1-3）。第一／二輪曾 fail／skip，見 §1.2 |

`pins` 這項做過負向測試（把 SHA 改回壞的那個跑一次，確認它報 fail 而不是假綠燈）。

```bash
uv run python scripts/check_workflow_guards.py                  # 全部（不含 rerun）
uv run python scripts/check_workflow_guards.py --only pins      # 只查釘住的 SHA
uv run python scripts/check_workflow_guards.py --only rerun --rerun 36690567806   # 3.1-3
```

`rerun` 每次都需要 `main` 比那個 run 的 sha 更新一輪才能有意義，所以它**不是**一次跑完就
永久有效的檢查——`main` 停在 `351e273` 的這段時間裡再跑一次，它會 skip（而不是假通過），
因為那三個候選 run 的 `41b2d57` 又變成 HEAD 了。

### 5.1 這支 harness 自己踩過的四個坑（都是它自己的 bug，不是 workflow 的）

留著當提醒——四個都是「看起來像在驗防護、其實壞掉」的類型：

| # | 坑 | 症狀 | 修法 |
|---|---|---|---|
| H1 | `gh_json()` 用來接 `gh api … --jq .sha` | `--jq` 印的是**裸字串**不是 JSON。commit sha 常以數字開頭（`41b2d57…` 被當成數字 `41` 再撞上 `b2d57`）→ `JSONDecodeError: Extra data: line 1 column 3` | 加 `gh_scalar()` 給純量用 |
| H2 | `gh run rerun` 的結果抓錯 run | rerun **沿用同一個 `databaseId`**、只把 `run_attempt` 加一。原本用「最新那個 run」去猜，會拿到別的 run 的結果——看起來像通過，其實查錯對象 | 一律重讀同一個 `run_id`，並比對 `run_attempt` 有沒有真的加一 |
| H3 | 沒扣掉 GitHub 合成的步驟 | 把 `Post Checkout repository`／`Complete job` 算成「guard 拒絕後還有步驟執行」，**把正確運作的 guard 報成 fail** | `is_synthetic()` 排除 `Set up job`／`Complete job`／`Post *` |
| H4 | 用 `status` 篩「有沒有執行」 | 被跳過的步驟在 API 上是 `status: "completed"` ＋ `conclusion: "skipped"`，篩 `status` 會把它們全算成執行過 | 篩 `conclusion` |

H3、H4 是一對：H3 修好後 H4 讓假警報換個方式回來。兩者都收在 `real_steps_after()`。

### 5.2 順帶一提：`gh run view --log` 每行有前綴

權限節錄的解析一開始拿到空結果，是因為每行其實是
`commit\tSet up job\t2026-09-30T07:54:17.8651003Z Contents: read`——前面有
`job<TAB>step<TAB>timestamp ` 前綴（有些行還帶 BOM），`^\s*KEY: value$` 抓不到。
用 `log_body()` 剝掉前綴再比對。

同樣的陷阱也影響「guard 有沒有真的報錯」的判讀：Actions 會把腳本原始碼 echo 出來，
所以 `echo "Run sha $GITHUB_SHA does not match …"` 那行**永遠**會出現在 log 裡。
要分辨「腳本原文」和「實際輸出」，得看有沒有 ANSI 色碼（`^[[36;1m`）——
實際輸出沒有顏色。3.1-1 的 guard 區段裡三個那樣的字串全部帶色碼，所以是原文；
3.1-2 的 `Ref refs/heads/phase1-spike is not refs/heads/main` 沒有色碼，是真的輸出。
`check_guard_branch` 因此只比對 `Ref refs/…` 這種**已展開**的形式。
