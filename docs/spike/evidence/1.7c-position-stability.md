## 2. 進行中匯出（M5a）

一邊生成（長回覆，600s timeout）一邊匯出，共 20＋次樣本：

- **每次都 rc=0、合法 JSON、無檔鎖、輸出可解析**；不需要互動。
- 從未匯出到「寫壞的 JSON」；但會匯出到**尚未完成的訊息**：最後一則 assistant 的 `time.completed` 缺席、text part 可能已含部分文字（0 → 8306 字元；Ej-1..3、Ex、Ey 樣本）。
- 前綴穩定性：Ej-1（3 則）→ Ej-2（4 則）→ Ej-3（4 則）→ final；各樣本之間既有訊息 id 前綴一致（`prefix_identical=True`），最後一則未完成訊息只會「長大」，不會換 id 或改位置。
- 結論：進行中匯出**安全、可解析、位置穩定**；同步器可用「最後一則 assistant 未 completed」辨識生成中快照（與 1.7b 的 caveat 相同）。

## 3. undo／編輯／revert（M5b）

### revert（API：`POST /session/{id}/revert {messageID}`）與 unrevert

對 E4（10 則）revert 到 index 2：

```bash
$ curl -s -X POST "$API/session/$SID/revert?directory=/work" -H 'content-type: application/json' \
    -d '{"messageID":"msg_0dca5c113001LOP1WMESoyDw13"}'
{"id":"ses_f235a894effes0cRw74MxQPLBb","revert":{"messageID":"msg_0dca5c113001LOP1WMESoyDw13"}}
```

- revert 後匯出：**messages 仍然是 10 則、id 與內容完全不變**；唯一改變是 `info.time.updated` 更新，以及 `info.revert` 多出指標。
  ```
  DIFF info.time.updated: … -> …
  ONLY_B info.revert.messageID
  STATS same=320 diff=1 only_a=0 only_b=1
  ```
- `unrevert`：`info.revert` 移除、其他不變（`diff=1` 僅 `time.updated`）。
- 即 revert **只是指標**，不移除訊息、不改變位置；接續點不受影響。

### 編輯（revert 到舊訊息後重新送新內容）

revert 到 index 2 後，以 `opencode run -s $SID` 送新內容（等效 TUI 的編輯後重送）：

- 匯出結果剩 **4 則**：`[0][1]` 為原訊息（同 id），`[2][3]` 是**新的** user／assistant（新 id）；原本 revert 點之後的舊訊息（index 2 起的舊 id）**從儲存中消失**（DB `message` 表也只剩 4 筆）。
- `info.revert` 已清空（`None`）；`EDITED-BRANCH-999` 出現在 `[2]`。
- 影響：**編輯會改寫位置**——被編輯點之後的訊息（含其 id）被刪除、由新 id 取代。因此「接續點」若在被編輯點之後即失效；被編輯點之前的訊息位置照舊。

### /undo、/redo

TUI 有 `session.undo`／`session.redo` 指令（binary 字串證實），語意與 revert／unrevert 相同（undo = revert 至最近 user 訊息、redo = unrevert）；皆為**指標**操作（同第 3.1 節）。

## 4. 接續點的表示：建議

1. **首選 message id**：既有訊息 id 在追加、重開、進行中匯出、revert／unrevert 下都不變；接續點寫成「在訊息 `msg_…` 之前（含）」。
2. 索引（index）也可用，但遇到編輯時與 id 一起失效；id 至少能精確指出「哪一則還在、哪一則被換掉」。
3. 編輯（刪除後重送）是唯一會使既有位置失效的操作；屆時提交流程可比對新舊快照的訊息 id 集合，把「接續點指到已不存在的訊息」判為拒絕或改指（此規則屬 3.7／3.10，回報 PM）。
4. 快照（完整匯出檔）可作為最後防線：本節所有樣本都在 `~/.local/share/aistorage-spike/work/oc17-main/`。
