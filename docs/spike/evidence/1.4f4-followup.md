## 1. H4 前半：`sha256Checksum` 可用且足以做驗證（PASS）

### 1.1 rclone 上傳的檔案，Drive API 回傳 `sha256Checksum`

對 `agora-1.4f3` 的三種檔案（manifest／bundle／annex 物件）以 `files.get` 取 `fields=size,md5Checksum,sha256Checksum,sha1Checksum`：

| 檔案 | size | md5Checksum | **sha256Checksum** | 與檔名內嵌值 |
|---|---|---|---|---|
| `GITMANIFEST--c2febd2f-…` | 473 | `b45c8c3e…` | **`81aad756d6a4701674083ae616fd7311331f7f84b7919c6a1f39112d63d1e39d`** | 等於釘選值 |
| `GITBUNDLE-s2679--…-fea4a9a3…` | 2679 | `84acdb3f…` | **`fea4a9a31d7b24d5a6ab2a11f501a2300fa05f31e9a05e4ea312a3bbb628a8a6`** | 等於檔名後綴 |
| `SHA256E-s204800--cda04a97….bin` | 204800 | `d12e44ef…` | **`cda04a975f86da471071ffa0587c2177a2e5a99c3196bae13e9c179a0817cfaf`** | 等於檔名（annex key） |

`files.list` 以 `fields=files(id,name,size,sha256Checksum,md5Checksum)` 亦回傳同值。→ **不需要下載內容就能驗證名稱與雜湊**；rclone 上傳的檔案也適用（Drive 會為二進位檔計算 sha256）。

### 1.2 metadata-only 版 snapshot 與清掃，結果與整份下載版一致

新增 `spike/probe/f3_meta_snapshot.py`、`spike/probe/f3_meta_clean.py`：判定規則與 `f3_snapshot.py`／`f3_clean.py` 相同，但 valid 來自 metadata；只有**被釘選值信任的 manifest**（小檔）才下載解析引用清單，bundle 內容只在需要重放時下載（`--content-dir`）。

- 正向（`02-meta-clean.txt`、`01-meta-snapshot.txt`）：乾淨的 `agora-1.4f3` 上，metadata 版保留 **同樣 7 筆**（2 manifest、4 bundle、1 annex），`media_gets=2`（只有 manifest）、`bytes=946`。
- 負向（`03-inject-negatives.txt`、`04-compare-cleaners.txt`）：注入四種攻擊形狀——垃圾同名 manifest、未被引用的同名 bundle、名稱與內容相符但**沒被任何 ref 引用**的 annex 物件、巢狀資料夾——兩個 cleaner 的**逐項決策完全相同**（機械比對 `IDENTICAL`，11 筆決策：8 KEEP、3 MOVE）。
- 成本（`07-h4-timing.txt`）：同一 repo，full-download snapshot **7.92 s／4,120 B**（manifest＋所有 bundle＋annex 物件）；metadata-only **2.73 s／946 B**（manifest 兩份）。在此小 repo 已是 4.4× 流量差；差距隨 annex 物件總大小線性放大（正式流程只在 refs 不符時才下載 bundle 重放）。

## 2. M3：兩階段釘選寫回 GitHub（PASS）

- workflow `pin-writeback-impl2.yml`（測試 repo，`permissions: contents: write`、`concurrency: pin-writeback-impl2`）以 **`GITHUB_TOKEN`** 把 pending／promoted 寫進專用分支 **`pin-state`** 的 `.pin/pin.pending.json`、`.pin/pin.json`；commit 身分是 `github-actions[bot]`。workflow 由**使用者本人**的 gh 身分觸發（`gh workflow run`），住民 PAT 沒有 contents 權限（1.6 已證）碰不到這條分支。
- 逐項：
  | 情境 | 結果 |
  |---|---|
  | 寫 pending（首次建分支） | **成功**：`pin-state` 分支建立、pending 內容正確（`m3-01-write-pending.txt`） |
  | promote（observed == pending） | **成功**：promoted 寫入、pending 刪除（`m3-02-promote.txt`） |
  | promote 故意失敗（`fail=true`，寫 promoted 前中止） | **失敗如預期**：promoted 仍是舊值、**pending 留在分支上**（`m3-03-fail-promote.txt`） |
  | 下一輪重跑 promote（observed == pending） | **自動恢復**：pending 轉正、pending 刪除（同上） |
  | promote（observed == promoted，pending 未生效） | **自動丟棄 pending**（`m3-04-drop-failclosed.txt`） |
  | promote（observed 兩者皆不符） | **fail-closed**：workflow 失敗、**pending 原樣保留**（未漂白、未誤刪） |
- 待 3.2 定案（review M3）：pending 與 promoted 同檔或兩檔、寫入原子性、concurrency group 保證單一寫者、`GITHUB_TOKEN` 推送的衝突處理。

## 3. M4：多層組乾淨重跑（PASS）

1.4f3 的 `43-multi-recursive.txt` 有一次未說明的 traceback：第一次建 `pin-multi.json` 時，shell 裡把「空 JSON」與真正的 refs JSON 串在一起丟給 python（`--expected-refs` 拿到兩段 JSON），replay 失敗、promote 沒執行；**當時 clean 用的 `trusted_manifest=1` 是舊的 `pin-multi.json`，而那份 pin 是稍後由另一個 python 區塊（`promote` 用 `snapshot` 的候選）補寫成功的**。證據鏈當時交代不完整。

本次重跑（`06-m4-multi-rerun.txt`）：

- `f3_round prepare`（多層前綴 `agora-1.4f3multi/inner`）：parents 兩層 OK、clean 0 移動、verify refs 與 manifest sha 等於 pin → **`prepare: OK`**。
- 從零重建釘選：`f3_snapshot` → `f3_replay_check`（唯一通過）→ `f3_pin promote`（單一 python 區塊、無 shell 拼接）→ rc=0；與原 `pin-multi.json` 逐欄位比對：`refs`／`manifest_sha256`／`manifest_name`／`manifest_bundles`／`annex_objects`／`state` **全部 SAME**。→ 原本的 pin 正確，M4 的重跑補上了完整、可重現的證據鏈。
