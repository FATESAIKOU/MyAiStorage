### 2.2 重要發現：manifest 內 `-` 開頭之已移除 bundle 行導致 `parsed=False`
在分析 manifest 內容時發現：
- `agora-load` 歷經 500 次 push，且設定了 `annex.max-git-bundles 10`。
- `git-remote-annex` 在執行 bundle consolidate 時，並未自 manifest 刪除舊 bundle 行，而是**在舊 bundle 檔名前面加上減號 `-`**（例如 `-GITBUNDLE-s485--...`）表示已移除/已合併。
- 在 514 行 manifest 中，僅有 **6 行**為有效作用中的 bundle（開頭為 `GITBUNDLE-s`），其餘 **508 行**均以 `-GITBUNDLE-s` 開頭。
- `f3_meta_snapshot.py` 第 124 行使用：
  ```python
  if lines and all(BUNDLE_RE.match(ln) for ln in lines):
      parsed = True
  ```
  因為 `BUNDLE_RE` 僅匹配 `^GITBUNDLE-s...`，導致包含 `-` 減號行的 manifest 被判定為 `parsed=False`，進而使 `f3_meta_clean.py` 判定引用清單為空而將 508 個舊 bundle 標記為 `would_move`。
- **影響與建議**：
  1. 對清掃成本量測無影響：無論 parsed 為 True 或 False，清掃腳本皆對全部 517 個檔案執行 metadata 列舉比對，且下載 2 份 manifest，因此量測出的時間、API 呼叫次數、下載位元組均 100% 反映真實成本。
  2. **列入 3.2 必要修正**：`f3_meta_snapshot.py` 之 manifest 解析正規表達式需支援 git-remote-annex 的減號語法（`-GITBUNDLE-...`），將其識別為歷史/已移除 bundle，或在驗證作用中引用清單時予以過濾，避免誤將真歷史 bundle 標記為不可信。

1. **排程空跑（Empty Schedule Run）**：
   - 1.8 實測：純收件匣掃描（未裝工具）耗時 8〜28 s（p50 11 s）→ 1 計費分鐘。

   - **單次空跑仍維持 1 計費分鐘**。
2. **主動觸發提交（Active Commit Run）**：
   - 1.8 實測：合成流程（安裝＋clone＋push＋驗證）耗時 37〜73 s（基準值約 39 s）→ 1 計費分鐘。
