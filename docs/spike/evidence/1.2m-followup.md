## M1：manifest 預檢的 fail-open 修正

### 修正內容（`spike/scripts/manifest_precheck.sh`）

1. **`rclone lsf` 失敗 → exit 2**（不再 `2>/dev/null` 吞掉後繼續）：錯誤導向暫存檔，只輸出**類別**（`not-found(404)`／`quota-or-rate-limit`／`auth(401)`／`permission(403)`／`network`／`other`），原始 stderr 不印出。
2. **`rclone hashsum` 非零退出 → exit 2**；**`sum` 為空 → exit 2**（fail-closed）；同樣只記類別。
3. 其餘語意不變：snapshot 寫入成功指紋（exit 0）／check 相同（exit 0）／不同（exit 3）／其餘環境錯（exit 2）。

### 測試（容器內；`m1-tests.sh`、`m1-tests.log`）

| # | 情境 | 方法 | 結果 |
|---|---|---|---|
| T0 | 正向對照（真 remote `agora-basic/`） | snapshot → check | `snapshot rc=0`、`check rc=0`（PASS） |
| T1 | lsf 失敗（不存在的 prefix） | `snapshot agora-1.2m2-nonexistent` | `rc=2`，類別 `not-found(404)` |
| T2b | **sum 空**（stub rclone：lsf 成功、hashsum 空輸出） | snapshot | `rc=2`，訊息「sha256 是空的……fail-closed」 |
| T2c | hashsum 網路錯（stub：`dial tcp … no such host`） | snapshot | `rc=2`，類別 `network` |
| T2d | hashsum 權限錯（stub：`Error 403: permission denied`） | snapshot | `rc=2`，類別 `permission(403)` |
| T3 | lsf 網路逾時（stub：`i/o timeout`） | snapshot | `rc=2`，類別 `network` |
| T4 | **check 端**也 fail-closed（合法快照後，hashsum 429） | check | `rc=2`（不是 0、也不是 3），類別 `quota-or-rate-limit` |
| T5 | 真 remote 負向：push 改變 manifest 後 check | `check` | `rc=3`（CHANGED 中止，與修正前一致） |

**負向對照（證明舊版真的 fail-open）**：以同一顆「lsf 成功、hashsum 空輸出」的 stub 跑**修正前**的腳本（`manifest_precheck_old.sh`，修正前存檔）：
- snapshot `rc=0`、寫出的指紋檔只有 25 bytes（只有檔名、沒有雜湊）；
- 再 check → **`rc=0`（PASS）** ——在同樣的錯誤下舊版放行。修正版在 T2b 是 `rc=2`。→ M1 的修正有效。

### 判定

**pass（M1 修正完成）**：lsf／hashsum 的任何失敗與空 sum 都中止（exit 2，fail-closed），錯誤只記類別；正向與 CHANGED（rc=3）行為不變。腳本改動在 `spike/scripts/manifest_precheck.sh`（工作樹內，未 commit）。

## M2：GITMANIFEST 替換窗口中斷（SIGKILL）

### 目標窗口的觀測

以 `m2-observe.py` 對一次正常 push（每 ~1 秒 `rclone lsjson` 輪詢）觀察 manifest 的生命週期：

```
[786ms]  manifest=[GITMANIFEST--d817d9a7-…] id=1SxAy0Y2  baks=1
[9104ms] manifest=[]                          ← 舊 manifest 刪除（進入窗口）
[11228ms] manifest=[GITMANIFEST--d817d9a7-…] id=18Fll0d6 ← 新 manifest 建好（窗口結束）
[12772ms] … baks=0（.bak 一度消失後又出現）
[14918ms] … baks=1（最終）
```

- 窗口（main manifest 不存在）約 **2.1 秒**（9.1s→11.2s）；期間 **`.bak` 仍在**（值＝push 前的舊 manifest 內容）。

### 中斷測試：一消失就 kill

`m2-killtest3.py`：push 起跑後持續輪詢；偵測到 main manifest 消失就對整個 process group `SIGKILL`。**乾淨嘗試全部命中窗口，共 9 次**（`killtest2` 4/4、`killtest3` 3/3、`bakprobe` 1/1、`bakcontent` 1/1；`killtest1` 的 1 次因前次意外自殺的殘留狀態不計）：

```
=== attempt 1: local HEAD=becc42ec | pre manifest={'GITMANIFEST--…':'1vw8op-t'} baks=1
  [WINDOW HIT] samples=24 t=18.16s
  IMMEDIATE after kill: manifest=[] baks=1
  clone A (no recovery): rc=0  HEAD=96e3f5f9（＝舊 remote head，不是被 kill 的 HEAD）
  re-push rc=0：96e3f5f..becc42e main -> main
  clone B (after recovery): rc=0  HEAD=becc42ec == killed HEAD? True
    new content intact=True  old content intact=True
```

### 三個狀態的結論

| 遠端狀態 | 全新 clone | 重新 push（用原 repo） | 已 commit 的內容 |
|---|---|---|---|
| 只有 `.bak`（窗口中被 kill；9/9 次命中，其中 6 次完成 clone 驗證） | **成功**（`rc=0`），讀到的是**舊** head（.bak 是前一次的 manifest） | 成功，remote main 前進到被 kill 的 commit | 沒有遺失 |
| main＋.bak **都不存在**（最壞情況，手動刪除兩者） | **失敗**：`git-remote-annex: No git repository found in this remote.` | 成功（`git push drive main git-annex` 重建 manifest），remote 恢復 | 沒有遺失（之後全新 clone 的 HEAD 與被 kill 的 commit 一致、`annex get` 內容相同） |

- 表中「6 次 clone 驗證」＝`killtest2` attempt 1、`killtest3` attempt 1〜3、`bakprobe`、`bakcontent` 各一次；其餘 3 次（killtest2 attempt 2〜4）命中窗口且成功 re-push，但 clone 步驟因測試腳本的暫存目錄未清而回 `rc=128`（`destination path already exists`，是腳本 bug、不是遠端狀態；該 3 次的 log 可見該錯誤字樣）。

- 「只有 `.bak`」時 clone 其實**讀得到**（`git-remote-annex` 會 fallback 到 `.bak`），代價是**短暫讀到舊版本**（與 git 的 pull 語意一致，不算損壞）。
- 「兩者皆無」時 clone 會**明確失敗**（不是靜默給出錯內容）；只要還有任何一個既有 clone（含提交流程的 runner 快取、管理者的本地 clone），一次 re-push 就能完整重建，**內容零遺失**——本測試的 9 顆 commit 與 annex 物件（含 2 MiB／4 MiB 大檔）在恢復後全部逐位元一致。
- 附帶事實：每次 push 後 `.bak` 內容＝**push 前**的 manifest；push 完成後主 manifest 與 `.bak` 會相同（見 `m1-realtest.log` 的 check 輸出：兩行雜湊相同）。

### 對 6.4 復原手冊的素材

1. `clone` 失敗且訊息是 `No git repository found in this remote.` → 遠端 manifest 完全消失；**不要重新 initremote**，直接在任一既有 clone 內 `git push drive main git-annex` 重建（本次實測成功）。
2. 只要 GITMANIFEST 或 `.bak` 任一存在，clone 都還能走；`.bak` 存在時可能 clone 到舊版本，屬正常（推回的動作會把遠端帶到最新）。
3. 重建後驗證：全新 clone 的 `HEAD` 與來源端一致、`git annex get` 內容 `cmp` 一致（本次以 3 顆大檔＋多顆小檔驗過）。
