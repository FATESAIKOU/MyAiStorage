# 讀寫分離：讀取介面只有一個並指定新鮮度，寫入機制依成本追加

相互參照（n↔m）時，一個 Session 要讀另一個還在進行的 Session，就會問「讀到的有多新」。最直接的做法是讓讀者在讀之前要求對方先同步、先提交，但那等於讓讀取反過來依賴寫入的實現方式：換一種寫入機制，所有讀者都要跟著改；讀者也會因此能觸發別人的寫入。所以讀寫分離：每個要素的讀取手段只有一個讀取介面，讀的時候可以指定新鮮度（最多落後多久），每筆結果都附快照時間；達不到要求時照樣回傳並附上警告，由讀者自己決定怎麼用。讀取絕不觸發同步或提交。一個 Session 在 Agora 能維持多新，由寫入端的機制決定，而寫入機制依成本選擇、逐步追加：期 1 只給最便宜的一組（定期同步、定時提交、寫入者主動同步並提交），之後再加縮短間隔、上傳後自動提交、自架 runner 等，讀取介面不變。

## Considered Options

- 讀取時觸發對方同步與提交：讀者一定拿到夠新的內容，但讀取依賴寫入的實現方式，讀者也得到了觸發別人寫入的能力。不採用。
- 達不到新鮮度就阻塞等待，直到逾時：呼叫端省事，但讀取的耗時變得不可預期，而且等待的前提是寫入端會在時限內提交，這又把讀者綁回寫入機制。不採用。
- 達不到新鮮度就回報錯誤、不給內容：語意最嚴，但讀者往往還是需要那份舊內容（知道它多舊就夠了），錯誤只會逼每個呼叫端都寫重試或降級邏輯。不採用。

## Consequences

- 期 1 的新鮮度大約是：沒人主動提交時最多落後幾小時；主動同步並提交之後，約等於一次提交流程的耗時。
- 讀者一定看得到快照時間，所以不會把舊內容誤當成最新；但警告可能被忽略，讀取介面的使用者（例如 opencode 的 skill）要把快照時間與警告帶進 AI 的上下文。
- 寫入者判斷「同步並提交」完成，也是透過讀取介面看到自己這份快照，不看某一次提交流程的執行結果（GitHub 的 concurrency group 會取消排隊中的 run）。讀寫兩邊都只以讀取介面為觀察點。
