# 「被別台刪掉」改用資料夾 ID（#164，#109 R2）

**這是行為變更**（單檔更新也受影響）。只改上傳更新時對「別台是不是已經刪掉這個 Session」的判斷，不改 Drive 上的檔案格式。

## 變了什麼

- **以前**：更新送出後，只要「複製前有、確認時列表沒有」的檔名就當成「copy 期間被別台刪掉」（#155 之前直接 purge 整個資料夾並另存；#155 之後先定向查詢）。別台正常清理（換掉被取代的 raw）、Drive 列表漏檔都可能被誤判。
- **現在**：比 `sessions/<ULID>/` 的**資料夾 ID**。送出前記一次、確認時再記一次；不同＝資料夾在這段時間被 purge 又被我們的 copy 重建，才 purge 並另存成新 Session。別台的正常清理不會改變 ID，檔名少了不再是證據。
- **存在檢查**：「Drive 上沒有這個 Session」現在也包含「資料夾裡有檔案、但沒有 `session.md`」（purge 之後第一個大段 copy 中途失敗留下的孤兒）。這種情況會另存成新 Session，不會把它補完而讓刪掉的 Session 復活。

## K.1 探針結果（真 Drive）

- 遞迴 `lsjson`（不加 `--files-only`）的目錄項帶 `ID`。
- purge 後同名重建（`mkdir` 與 `copy`）都拿到**新** ID。
- `ModTime` 是本機 mtime。
- 定向 `lsjson`：資料夾不存在＝rc=3＋`directory not found`；存在但空＝rc=0 零筆；斷網＝rc=1。

## fail-closed 是什麼意思

「看不清楚就不動」：

- 列表沒帶目錄 ID 時，送出前與確認各補一次 `lsjson gdrive:sessions --dirs-only`；兩次都拿不到 ID，這一筆更新**不送**，留在 outbox 並警告，下一輪再試。
- 判定被刪之前一定先對該 ULID 做定向查詢（與 #152 同一個函式）：只有 rclone 明說資料夾不存在（或資料夾有檔卻沒有 `session.md`）才另存；查得到、查到空、查不動、逾時都當「不確定」，不 purge、不另存，留在 outbox。確認階段 ID 變了，還要資料夾裡有 `session.md` 且**只有**這一輪送出的檔才 purge；多出別人的檔就是活的資料夾，留著。
- 列表本身失敗（退出碼非 0）時，整批不做刪除判定。

## 對效能與使用者的影響

正常輪次的 rclone 次數不變（更新約 7 次）；列表沒帶目錄 ID 才多 2 次（上限 9）。只在「列表少了資料夾」或「確認時 ID 變了」才多一次定向查詢。沒有要使用者做的事。
