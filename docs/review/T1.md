# Review：需求單 T1（指令模式：pull／push、批次動作的進度與續傳）

2026-10-03，review。對象是 `docs/tickets/T1-command-batch.md`（`de4360e`）。我也一併對照了目前的 design（特別是 5.4 第 6 點：**continue 寫回同一個 id**，`109c150`／`3011d15`）和 `store.sync` 的現況。只提意見，不改程式，也不改需求單。依照指示，沒有跑整合測試、沒有碰 Drive，也沒有讀任何真實的 Session。

## 結論

R1～R3、R5、R7 都很清楚，也解決了 cache.md 的 K1、K2。**需要在實作前先補進需求單的，主要是 R6**：「同步時保留雲端已經沒有的 Session」這件事，會影響到**每一個會存檔的指令**，而需求單只寫了 pull 和 push 的行為。

## Q1（High）：R6 會讓 continue／edit／import 悄悄復活被刪掉的 Session

- R6：同步時**保留**別台機器刪掉的 Session（鏡像和索引都留著，標成「雲端沒有」）。
- 5.4 第 6 點（使用者 2026-10-02 的決定）：continue 結束之後，會**寫回原本那個 agora id**。
- 所以：A 機器刪掉了 X；B 機器同步之後，X 還在 B 的索引裡；B 用 `continue session X` → `_save` → `stage` → `push_one`，就會把 `sessions/X/` 整個傳回 Drive。**X 在所有機器上都回來了**，B 的使用者完全不知道這件事，也沒有加過 `--not-exist-upload`。
- 同樣的事也會發生在：`edit session X`（`_save`）；`import`，當它的來源 agent session 透過 `by_source` 對到 X 時（「內容沒變但有 --header」或「內容變了、沒有子 Session」都會寫回 X）；以及 T2 互動模式裡對 X 做的任何寫入。
- **建議**（寫進 R6）：所有**寫回既有 id** 的指令（continue、edit、import 的更新路徑），遇到「雲端沒有」的 Session，一律**拒絕**，exit 1，並且印出兩個選擇：「`agora push session X --not-exist-upload`（把它救回來），或 `agora pull session X --not-exist-delete`（在這台機器上也刪掉）」。import 的話，也可以改成**建一個新的 Session**（和 S7「已經有子 Session 就分岔」同樣的處理），不寫回 X。新建的 Session（merge、import 新的來源）不受影響。

## Q2（High）：`pull --not-exist-delete` 會刪掉還沒上傳的 Session

- outbox 裡的 Session（上傳失敗的那些，N13），在雲端「沒有」，但它們不是被刪掉了，而是**還沒上去**；本機的那一份往往是唯一的一份（S2）。
- 只要使用者把 search 的結果整個接給 `pull --not-exist-delete`（需求單鼓勵這種用法），這些 Session 就會被刪掉。
- **建議**：(a)「雲端沒有」的定義改成「雲端沒有，**而且**不在 outbox 裡」，outbox 裡的那些應該標示成「未上傳」（現有的 C11），兩者分開；(b) `--not-exist-delete` 遇到在 outbox 裡的 id，就拒絕刪除，印出「agora:X 還沒上傳，不刪；要傳上去請等下一個指令，或者執行 `agora push session X`」；(c) 用單元測試鎖住。
- 同樣的道理，pending 裡記著的、還在接續中的 Session，也不能刪。

## Q3（Medium）：R6 對其他指令的影響

| 指令 | 現在（同步時會清掉雲端刪除的） | R6 之後（保留，並且標成雲端沒有） | 建議寫進需求單 |
|---|---|---|---|
| search | 搜不到 | **搜得到**，而且看不出它在雲端已經沒有了 | 輸出那一行的最後加上 `(雲端沒有)`（和 `(未上傳)` 一樣）；新增 `--filter cloud=no`／`cloud=yes`，管線就可以寫成 `agora search session --filter cloud=no \| … \| agora pull session --not-exist-delete` |
| show | 找不到 | 看得到 | 在第一行標示「雲端沒有」 |
| continue／edit／import 的更新 | — | 會悄悄復活 | 見 Q1 |
| merge | — | 雲端沒有的 Session 也能被當成來源；新 merge 的來源清單裡，`agora show session <id>` 在其他機器上會找不到 | 來源裡有雲端沒有的，就拒絕（或者至少警告） |
| delete | 找不到 | `delete_session` 會對雲端不存在的資料夾執行 `rclone purge`，結果是 StoreError，exit 2 | 雲端沒有的，只刪本機的副本，exit 0，訊息寫明「雲端早就沒有了，只刪了本機」 |
| delete 的子 Session 檢查 | 雲端刪掉的子 Session 已經被清掉，不會擋 | `children()` 會掃到**雲端已經沒有、但本機還留著的子 Session**，擋住父 Session 的刪除 | `children()` 不計入雲端沒有的；或者擋的時候，訊息寫明「子 Session agora:Y 雲端已經沒有了，先 `pull --not-exist-delete agora:Y`」 |
| import 的 `by_source` | 雲端刪掉的不會被對到 | 會對到雲端沒有的那一筆，然後寫回去（Q1），或者被當成「已經匯入過」而略過（未匯入頁也就不會再列出那個 agent session） | `by_source` 預設排除雲端沒有的，讓它重新匯入成一個新的 Session |
| S7（有子 Session 就分岔） | — | 雲端沒有的子 Session 也會被算進去 | 和 delete 一樣，不計入 |

## Q4（Medium）：「雲端沒有」的判斷要怎麼做才安全

- 只有在**這一次列檔完整成功**、而且 `sessions/` 存在的時候（N12），才可以把「本機有、雲端沒有」的 ULID 標成雲端沒有。列檔失敗（離線、token 失效，或者 `list_sessions()` 回傳 None）時，**一個都不能動**，也不能把已經標成雲端沒有的「清除標記」。
- 雲端又出現了（例如另一台機器 `--not-exist-upload` 傳了回去）：下一次同步時，要自動清除這個標記。
- 單元測試：列檔失敗 → 沒有任何一筆被標記；`sessions/` 不存在 → 沒有任何一筆被標記；X 被刪掉 → X 被標記；X 又回來了 → 標記被清除；outbox 裡的不會被標記（Q2）。
- **索引的遷移**：如果「雲端沒有」是用 `sessions` 表的新欄位來記，現有的 `index.sqlite` 用的是 `CREATE TABLE IF NOT EXISTS`，新欄位不會自動加進去，INSERT 就會因為欄位數量不對而失敗。需要用 `PRAGMA user_version` 判斷，版本不一樣就重建索引（它本來就是可以重建的快取），或者另外開一張 `cloud_missing(ulid)` 表。

## Q5（Medium）：pull 的 id 混合

| 情況 | 需求單 | 建議 |
|---|---|---|
| 沒有前綴的 id（`01M…`、`ses_…`、uuid） | 沒有寫 | 其他指令都接受沒有前綴的 ULID（`_ulid_of`），pull 也一樣，**沒有前綴就當成 agora**。`ses_…`／uuid 一定要加上 `opencode:`／`claude:`，否則報錯（不要用形狀去猜） |
| `--not-exist-delete` 搭配 `opencode:`／`claude:` 的 id | 沒有寫 | 意思應該是「agent 那邊已經沒有這個 session 了，就刪掉它在 `reading/` 的快取」，和 K7 一致。或者寫明「這個 flag 只對 agora 的 id 有作用，對 agent 的 id 會被忽略，並且印一行說明」 |
| `agora:` 的 id 不在本機的索引裡 | 沒有寫 | 先做一次不節流的同步；雲端有，就拉下來（session.md 和 raw）；雲端也沒有，就 exit 1，「找不到」 |
| `opencode:`／`claude:` 的 id，在這台機器上找不到 | 沒有寫 | 這一筆記成失敗，照樣做下一個（R2／K5 的原則），最後 exit 2 |
| 同一個 id 給了兩次 | 沒有寫 | 去掉重複，k/N 的 N 用去重之後的數量 |
| 管線：`agora search … \| agora pull session` | R5 說「從 search 用管線接過來」 | 寫明是用 `xargs`（`agora search session --filter … \| cut -d' ' -f1 \| xargs agora pull session`），還是 pull／push 會在沒有給 id、而且 stdin 不是 TTY 時，從 stdin 讀 id（每行取第一欄）。後者比較順手，也不會違反「不給 id 就報錯」（TTY 上不給 id 還是報錯） |

## Q6（Medium）：R4 merge 沿用要約的鍵

需求單寫的鍵是「agent＋提示詞版本＋來源 id＋那個來源的內文」。

1. **少了模型**：opencode 可以用 `AGORA_OPENCODE_MODEL` 換模型，使用者的預設模型也可能會變。如果沿用的是別的模型寫的要約，`generated.by`／`agora.merge.by`（現在是從**這次**有呼叫的模型組出來的）就會記錯，也和使用者「換一個模型重寫」的意圖相反。**建議**：鍵要包含「這次選的模型設定」（環境變數的值；沒設的話是 `default`），快取裡也存下實際回答的模型，沿用時把它算進 `by`。
2. **「內文」要明確**：建議用「**實際送出的整段 prompt**」（`SUMMARY_PROMPT` 加上截斷之後的來源文字）的 sha256 當作鍵。這樣，提示詞改了卻忘了把版本號加 1、`SOURCE_MAX` 改了、來源被 continue 寫回去（現在 continue 會改到同一個 id 的內容）這幾種情況，都會自然失效，不會沿用到舊的要約。來源 id 和 agent 也放進鍵裡，方便除錯。
3. **沿用時也要驗證**：用現在的 `SECTION_SCHEMA` 驗證快取的內容（A2 的原則），驗證不過就當作沒有快取。
4. **寫入要原子化**：用唯一的暫存檔名再 rename（K4 的原則），兩個 merge 同時跑時才不會壞掉。
5. **清理**：寫明什麼時候刪。建議 merge 成功之後，刪掉這次用到的那幾份；中斷的話就留著；另外，超過 N 天的也刪掉。
6. 中斷的時間點：如果是在 opencode 的 summarize **還在執行**時按 Ctrl-C，那個 opencode session 的 id 還沒被記下來（v6 Z2），就會留下一個孤兒。這不是 R4 造成的，但「重跑」會讓這種情況更常發生，可以在需求單裡列為已知的問題。

## Q7（Medium）：push 時本機沒有 raw

- 鏡像預設只有 `session.md`，raw 要等到用到時才會下載。R7 說「只傳 `session.md` 和它指到的那個原始檔」，但本機可能**根本沒有**那個原始檔。
- **建議**：(a) 雲端有這個 Session、本機沒有 raw：只傳 session.md（如果雲端的 raw 和標頭的 md5 一致，就不必再傳）；(b) 雲端沒有、加了 `--not-exist-upload`、本機也沒有 raw：**拒絕**，「本機沒有 agora:X 的原始檔，傳回去也是壞的」；(c) 上傳的順序照 S1：先傳 raw，再傳 session.md，最後用 md5 確認（可以直接重用 `push_one` 的順序和驗證）。

## 和既有規則的對照

- R7 直接解決了 cache.md 的 K1（復活）與 K2（排除清單），方向正確。但 Q1 是 R6 帶進來的**另一條**復活路徑，需要另外處理。
- R6 刻意讓「刪除」不再自動傳到其他機器上，這和 design 5.6／第 6 節「要刪就是刪掉 Drive 上的資料夾，下一次 sync 時鏡像也會跟著刪掉」不一致。design 5.6、4.3 要一起改，並且寫明「其他機器上要用 `pull --not-exist-delete` 才會清掉」。
- 「索引要能回答這個 Session 雲端有沒有」：這也會影響 T2 的「雲端」欄、搜尋的標示（Q3）與寫入時的拒絕（Q1），建議在需求單裡定義成**一個欄位、三種狀態**：`有`／`未上傳`（在 outbox 裡）／`雲端沒有`（Q2、Q4）。
