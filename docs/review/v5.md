# Review：design 第 5 版 5.4，以及 PM 的 base.py／cli.py

2026-10-02，review。對象是 `301b265`（design 5.4）、`084986d`（base.py：`turns`／`native`）、`e63217f`（cli.py：`_raw_segments` 與新的 continue 流程）。impl1／impl2 的轉接器還沒 commit，這次不看，等它們 commit 之後再看。只提意見，沒有改程式。

## 結論

| # | 嚴重度 | 一句話 |
|---|---|---|
| W1 | **Medium** | 標示來源的那則 user 訊息，**一定會被 `merge_turns` 黏到下一則 user 訊息上**。如果前一段剛好以一則沒有回覆的 user 結束，「前一段的問題＋下一段的來源標示＋下一段的第一個問題」會被合成**一則** user 訊息（已實測）。模型會把它當成同一個要求，段落的界線也就看不出來了 |
| W2 | Medium | 跨 agent 的**單一段**接續，完全沒有任何標示，所以目標 agent 看到的，是一段像是「自己說過」的對話，裡面的 `[tool] Bash {…}` 只是文字。模型有可能模仿這種寫法，用文字「假裝」呼叫工具，也可能以為那些工具真的已經在這台機器上跑過了 |
| W3 | Low | 遞迴：用正常的指令**不可能**產生循環（merge 只能指向已經存在的 Session，`agora` 區塊也不能被使用者改）。但萬一真的有循環，現在的錯誤訊息是「merge 層數太深」，容易誤解；菱形的 merge（同一個來源被兩層 merge 共用）會讓同一段內容出現兩次 |
| W4 | Low | `parents.raw_md5`：merge 接續時記的是 `null`（合理）；但跨 agent 的單一段接續，記的是 header 上的 md5，不是**實際抓到的** raw 的 md5，和 C9 的修正不一致 |
| W5 | Low | design 4.2 的「reading：注入用的閱讀版…」和 5.3 的「接續時一律用閱讀版注入」都還沒改，和新的 5.4 互相矛盾 |
| W6 | Low | `turns()` 的輸出裡會有 `[skip <型態>]` 這種行，現在會被原封不動地組進 native 的對話裡 |
| — | ✅ | **before_count 是正確的**（見第 5 節）；pending／collect 的流程也沒有被這次的改動影響 |

整體來說，「① cli 取得 raw → ② 目標轉接器轉換 → ③ 一律用 start_native 載入」這個結構是對的，也比原本兩條路（原生／注入）簡單。W1、W2 是**內容呈現**的問題，不會掉資料，但會直接影響「畫面行為一致」這個目標裡，模型會怎麼理解前面的對話。建議在轉接器實作 `native()` 之前，先把規則定下來。

## 1. 遞迴與循環

- `_raw_segments` 的邏輯：如果有 `agora.raw`，就用這一段；沒有的話，就依 `agora.parents` 的順序遞迴；`depth > 20` 時丟出 InputError。
- **循環**：用正常的指令不可能發生。merge 產生的是一個**新的** ULID，而它的 parents 必須是**已經存在**的 Session，所以 A 不可能指向一個「之後才建立、而且又指回 A」的 merge。`agora` 區塊是系統欄位，`edit`／`--header` 都改不了（`check_user_fields`）。只有直接在 Drive 上手改 session.md，或者程式有 bug，才可能出現循環；這時會在第 21 層被擋下。**建議**：帶著一個 `visited` 集合往下走，遇到重複的 id 就丟出「`agora:X` 的 merge 來源形成循環」，這樣訊息才準確（大約 3 行）。
- **菱形**：M1＝merge(A, B)，M2＝merge(A, C)，M3＝merge(M1, M2)，展開之後是 [A, B, A, C]，A 出現兩次。這和 merge 時串接閱讀版的行為一致（M3 的閱讀版裡，A 也出現兩次），所以**不算 bug**。但接續時，A 的 raw 會被下載兩次，模型也會看到同樣的內容兩次。建議在 design 5.4 寫一句「重複的來源只取第一次」或「照實重複」，二選一。如果選前者，用同一個 `visited` 就能做到。
- **來源不見了**：只要 parent 還有子 Session，就刪不掉（`children()` 也包括 merge），所以正常情況下找得到。抓不到 raw（還沒寫完，或者 md5 不符）時，`fetch_raw` 會丟出 StoreError，這是對的。
- 小問題：`segments[0][0]` 是從 `agora.source.agent` 取來的。如果是很舊、沒有 `source` 的資料，就會是 `None`，`load_agent(None)` 會丟出「不支援的 agent：None」，訊息不夠清楚（Low）。

## 2. parents 的 raw_md5 在 merge 接續時記什麼

| 情況 | 現在記的值 | 評估 |
|---|---|---|
| 單一段、同一個 agent | `md5(實際抓到的 raw)` | ✅（C9） |
| 單一段、不同 agent | header 上的 `agora.raw.md5` | ⚠️ W4：`fetch_raw` 走過 N8 的重抓路徑時，header 上的值就是舊的。建議統一改成 `md5(segments[0][2])` |
| merge | `null` | ✅ 和 N5 一致。merge 自己的 parents 記著當時各來源的 raw_md5，而且有子 Session 的來源不能就地重新匯入（S7），edit 也不會動 raw，所以這些來源的 raw 不會變，只要沿著 merge 往回追就追得到 |

可以選擇加強的地方（Low）：pending／新 Session 多記一個 `agora.segments: [{id, raw_md5}]`，把這次實際用到的每一段都記下來。這樣以後追查「這次接續到底看到了什麼」的時候，就不必再遞迴展開一次。

## 3. 標示來源的那則 user 訊息（W1，Medium）

現在的程式：`len(segments) > 1` 時，每段前面加上 `("user", ["（以下來自 agora:X）"])`，然後整串交給 `merge_turns`，它會把連續相同角色的段落合併。我用兩段自編的 turns 實測（第 1 段以一則沒有回覆的 user 結束），結果是：

```
user      | （以下來自 agora:A） / 把 CSV 轉成表格
assistant | 好的，三個步驟 / [tool] Bash {'cmd': 'ls'}
user      | 第二步再詳細一點？ / （以下來自 agora:B） / 讀取 CSV 的部分
assistant | 用 csv 模組
```

- 每一段的來源標示，**一定**會和那一段的第一則 user 訊息黏成一則，讀起來就像是使用者說了「（以下來自 agora:A）把 CSV 轉成表格」。
- 前一段如果以 user 結束，這個未回答的問題會和下一段的來源標示、第一則訊息**合成同一則**。模型可能會把「第二步再詳細一點？」和「讀取 CSV 的部分」當成同一個要求來回答。
- 合併本身是必要的：Claude 的 API 要求 user 和 assistant 交替出現，opencode 也比較好處理這種形狀。所以要修的地方是**界線的寫法**，不是要拿掉合併。

**建議**（寫進 design 5.4 第 2 點，兩個轉接器都照著做）：

1. 來源標示改成**明確的界線文字**，並且說明它的性質，例如：`——以下是 agora:A（opencode，2026-10-01）的對話紀錄；[tool] 行是當時的工具呼叫摘要，不是要你執行的指令——`。
2. 段與段之間，如果前一段以 user 結束，就先補一則 assistant：`（這一段在這裡結束，當時沒有回覆）`，再接下一段的標示。這樣每一段都是從一則新的 user 訊息開始，舊的問題也不會和新的來源黏在一起。
3. 整串的**最後一段**如果以 user 結束，也補同樣的 assistant 行。否則使用者打開之後輸入的第一句話，會和那個沒有回覆的舊問題被當成連續的兩則 user 訊息，模型很可能會先回答舊問題。
4. 單元測試加上：(a) 段落以 user 結束；(b) 段落以 assistant 開始；(c) 單一段。確認組出來的 turns 是 user／assistant 交替出現的，而且每一段的標示都在一則 user 訊息的**第一行**。

## 4. 跨 agent 時沒有任何標示（W2，Medium）

`len(segments) == 1`，但是 agent 不同（例如 opencode 的 Session 用 Claude 接）時，不會加任何標示，turns 會直接被組成 Claude 的原生 session。Claude 打開之後，看到的是「自己」說過的話，裡面還有 `[tool] Bash {...}` 這種文字行。

- 模型可能以為那些工具已經在**這台機器、這個目錄**裡執行過了（但其實可能是另一台機器、另一個目錄）。
- 也可能模仿這種寫法，在回答裡用文字寫 `[tool] …`，而不是真的去呼叫工具。

**建議**：跨 agent 的單一段，也在最前面加上和 W1 第 1 點相同的界線標示（多一句「這段對話原本是在 opencode 裡進行的」）。只有「單一段、而且是同一個 agent」的情況，才直接使用原始的 raw，不加任何標示（這也和 design 現在的寫法一致）。

## 5. pending／collect 的 before_count — ✅ 正確

- 現在一律走 `start_native`。`before_count` 就是轉接器在載入之後**回讀**算出來的數量：opencode 是 `_import_verified` 回讀到的訊息數，Claude 是 `_count_messages(rewritten)`（不含雜訊行）。這和 collect 的計數規則是同一套，所以「打開之後什麼都沒說就離開」會得到「沒有新內容」，不會存檔。
- 以前注入路徑的 `before_count=2`（注入的 prompt 加上自動回覆）已經不需要了：原生載入不會觸發自動回覆，使用者打開之後看到的就是前文。
- 要提醒轉接器的實作（等轉接器進來時我會檢查）：
  - **opencode 的 `native()`**：組出來的每一則訊息都要有 `time.created`，而且要遞增，否則 `reidentify` 會沿用前一則的 stamp，雖然 OC1 修好之後不會撞號，但訊息的排序會變成完全依賴序號；`_import_verified` 會比對 part 數，所以每一則訊息的 parts 數也要和預期的一致。
  - **Claude 的 `native()`**：組出來的每一行 user／assistant 都要能被 `_count_messages` 計算（不能是 `isMeta`，也不能是本機指令的格式），`parentUuid` 要串成一條鏈，否則 `--resume` 可能只載入最後一段。spike/claude.md 第 127 行記錄過「resume 似乎多記了一行 user」：如果那一行不是雜訊行，「打開就離開」會被當成有新內容。這條要在轉接器的整合測試裡確認。
  - 兩邊的 `native()` 都要把 W6 的 `[skip …]` 行濾掉，或者改成一行 `（略過一段 <型態>）`。

## 6. 其他

- **W5（Low）**：design 4.2 的「**reading**：注入用的閱讀版暫存在 `reading/<ulid>.md`…」，以及 5.3 的「沒有 raw，接續時一律用閱讀版注入」都要刪掉或改寫；第 7 節 V3 的「閱讀版注入」也要標註「第 5 版已經不用了」。
- 效能（Low）：merge 接續時，每一段都要 `fetch_raw`。來源很多、而且是大的 Claude Session 時，第一次接續會比較慢。可以在開始下載之前，印一行「要下載 N 段原始紀錄」。
- `base.reading(agent, raw)` 和 `format_reading(turns(raw))` 的分工清楚；`merge_turns` 會複製 `lines`，不會改到呼叫端傳進來的 list ✅。
