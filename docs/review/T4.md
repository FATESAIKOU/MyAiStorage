### K1（Medium）：export 的標題會是本機指令

新的 `_session_title` 對每一行都直接呼叫 `_title_of(o)`，**沒有先看 `_is_noise`**。舊的版本在 user 這一類有 `and not _is_noise(o)`。而 `_title_of` 本身也不看 noise（清單那一邊之所以沒事，是因為 `_said` 已經先把 noise 過濾掉了）。

結果是：一個以 `/model`、`/clear` 這類本機指令開頭的 Session，**匯入之後**的標題是 `<command-name>/model</command-name>`，而未匯入頁那一列顯示的是正確的標題。C2 本來是要讓這兩邊一致，這種情況反而變成了不一致。現有的測試沒有抓到。

**修法**：`_session_title` 跳過 `_is_noise(o)` 的行（或者讓 `_title_of` 自己檢查）。補一個測試：第一行是本機指令時，export 和清單的標題都是那一句真的話。

### K2（Medium，取決於真實檔案的欄位順序）：`last_message` 改成用 regex 判斷種類

以前，`last_message` 是先 `json.loads` 整行，再看 **`o["type"]`**。現在走 `_said`：先用 `_TYPE_RE` 在**原始的那一行文字**裡找**第一個** `"type": "…"`，再決定要不要看這一行。如果 assistant 那一行裡，巢狀的 `message.type`（`"message"`）或 `content[].type` 排在最外層的 `type` 前面，regex 拿到的就是 `"message"`，這一行就被略過了，預覽會變成更早的那一則 user。

- 測試用的 fixture（`tests/fixtures/claude/cl-basic.jsonl`）每一行的 `type` 都排在第一個欄位（我只看了欄位的順序），所以測試抓不到這種情況；
- 真實的 Claude Code 檔案是什麼順序，我不能讀真實的 Session 來確認，`docs/spike/claude.md` 列的欄位也是照字母排的，看不出順序。

**修法**（成本幾乎是零）：`_said` 把 regex 只當成便宜的預先過濾（這一行裡**有沒有**出現 `"type":"<kind>"`），真正的種類用 `json.loads` 之後的 `o.get("type")` 來決定，並且以它為準。補一個 fixture：巢狀的 type 排在前面的 assistant 行。

### K3（Low）：B1 也把「小數」改掉了

舊的 claude 是 `float(...)`，所以 `"1.5"` 是 1.5 秒；新的共用 `env_seconds` 是 `int(...)`，`"1.5"` 會退回預設的 600。proposal 的 B1 寫的是「看不懂的值」退回預設；`"1.5"` 以前是看得懂的。

**建議**：`env_seconds` 改成 `float`，或者在 proposal 寫明「只接受整數秒」。

### K4（Low～Medium，文件）：C2 本身就是行為的改變，proposal 沒有列出來

proposal 說「**行為不變**，例外有兩項（B1、B3）」，但 C2 改了標題的規則：
- 清單：前 40 行裡，**summary 現在會蓋過**比它早出現的 user 標題；而且如果有好幾個 summary，**最後一個**會贏；
- export：summary 是空字串時，以前會直接回傳 None（不再看 user），現在會繼續往下找。

我在 adapters-size 的 C2 有寫「標題的結果可能會變；統一是好事」，所以這個方向是預期的；但 proposal 要把 C2 列成第三個例外。另外還有一個小地方沒有統一：**多個 summary 時**，清單取的是前 40 行裡的**最後**一個，export 取的是**第一個**，兩邊還是可能不一樣。

### K5（Low，之前就有）：search 也用同一個 regex

`search_text` 在 T4 之前就是用 `_TYPE_RE` 判斷種類（探測裡兩個版本都找不到 assistant 那一句「步驟」）。如果真實檔案是巢狀 type 在前面，assistant 說的話就搜不到。這不是 T4 帶進來的，但 K2 的修法會一起修好它。
