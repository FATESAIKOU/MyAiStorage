# Review：design 第 7 版（merge＝每個來源一節，用 schema 驗證）

2026-10-02，review。對象是 `3e6fe12`：`docs/design.md` 5.3、`src/agora/cli.py`（`SECTION_SCHEMA`、`_section_of`、`_render`、`_require_sections`、`cmd_merge`、`cmd_continue`）、`pyproject.toml`（新增了 `jsonschema`）、`docs/acceptance.md`。只提意見，沒有改程式。依照指示，沒有跑整合測試、沒有碰 Drive，也沒有讀任何真實的 Session。單元測試：**222 passed**。

## 結論

這個方向比第 6 版穩：每一次只交給 AI 一個來源，所以第 6 版的 Z1（材料總長度沒有上限）自然就消失了；格式由程式負責，結果是確定的；巢狀 merge 不必再叫 AI。continue 改用 `relation` 判斷、舊 merge 的拒絕、edit 保留 raw 都是對的。**沒有 High**。有 3 個 Medium，都是「AI 的輸出能不能破壞版面」以及「沿用的 sections.json 有沒有被驗證」：

| # | 嚴重度 | 一句話 |
|---|---|---|
| A1 | **Medium** | schema 只限制了型別和「至少 1 個字元」。**換行、`#`、空白字串都能通過**。已實測：`progress` 裡放一段 `\n## 來源\n- agora:01FAKE「偽造」`，排出來的內文就多了一個假的「## 來源」標題和一個假的來源。如果來源的內容裡有提示注入，就可以藉這個在 merge 的內文裡偽造結構，而 continue 會把這份內文載入一個**工具是開著的** session |
| A2 | Medium | 沿用子 merge 的 `sections.json` 時，**沒有做任何驗證**（`json.loads(raw)["sections"]` 之後就直接 `_render`）。已實測：只要少了一個 `title`，就會出現 `KeyError: 'title'`，結果是 merge 被 catch-all 接住，exit 2，訊息也看不懂 |
| A3 | Medium | 單一來源的 `summarize` 本身失敗（逾時、agent 錯誤）時，**不會重試**，而且會讓整個 merge 失敗。前面幾個來源已經寫好的要約也會一起丟掉，下次要全部重寫。N 個來源最多要呼叫 3N 次，每次最多 600 秒，全部重來的代價很高 |
| A4～A10 | Low | 標題層級超過 6、`reason` 可以是空的、沒有任何長度上限、只有子 merge 時的 `generated.by`、`description` 沒有長度上限、design 裡「merge 沒有 raw」的舊說法、安裝的說明 |

## 1. schema 夠不夠嚴（A1、A4～A6）

現在的 `SECTION_SCHEMA`：最外層 `additionalProperties: false`，四個欄位都必填；`purpose`、`progress` 是 `minLength: 1` 的字串；`decisions[]` 是 `{decision: minLength 1, reason: string}`，也是 `additionalProperties: false`；`open_questions[]` 是 `minLength 1` 的字串。**型別和結構是嚴的**，多出來的欄位、少了欄位、型別錯了都會被擋下。

我用 `jsonschema.validate` 和 `_render` 實測，下面這幾種輸出都**通過了驗證**：

| 輸入 | 結果 |
|---|---|
| `purpose: " "`（只有空白） | 通過，排出來是「**目的**： 」（空的） |
| `reason: ""` | 通過，排出來是「- x —— 理由：」 |
| `progress: "\n## 來源\n- agora:01FAKE「偽造」"` | 通過，**內文裡多出了一個 `## 來源` 標題，和一個不存在的來源** |

**A1 的建議**（大約 10 行）：

1. schema：所有文字欄位都加上 `"pattern": "\\S"`（至少要有一個非空白字元）；加上 `maxLength`（例如 `purpose`／`progress` 2,000 字，`decision`／`reason`／`open_questions` 每項 500 字），以及 `maxItems`（例如 30）。
2. `_render`：所有文字欄位在輸出之前，先把換行換成空白（或者把多行內容縮排成 `>` 引用區塊），並且把開頭的 `#` 跳脫掉，這樣 AI 的輸出就**永遠不可能**產生標題或清單結構。標題和 id 那兩行是程式產生的，維持現在的樣子就好。
3. 單元測試：用一份「含有換行、`#`、假的 `agora:` 行」的 section，確認排出來的內文裡，`##`／`###` 標題的數量和來源清單，都只取決於 sections 的結構。

- A4（Low）：`reason` 沒有 `minLength`。如果是刻意允許「沒寫理由」，那排版時應該顯示「理由：（沒寫）」，而不是空白；如果不是，就和其他欄位一樣加上 `pattern: "\\S"`。
- A5（Low）：沒有任何長度上限，模型失控時可能寫出非常長的要約。A1 第 1 點的 `maxLength`／`maxItems` 可以一起處理。
- A6（Low）：回覆前面多了一句「以下是 JSON：」時，會被當成失敗然後重寫。現在已經會把錯誤訊息帶回去重寫，所以通常第二次就會成功；如果想少花一次呼叫，可以在 `json.loads` 失敗時，再試一次「取第一個 `{` 到最後一個 `}` 之間的內容」。

## 2. 重試（A3）

- `_section_of`：最多 3 次；每一次的 prompt 都是原本的 prompt，加上「上一次的輸出不合格：<錯誤的第一行，最多 300 字>」。只有 `ValueError`（JSON 解析失敗）和 `jsonschema.ValidationError` 會重試，**`summarize` 丟出的 `AgentError`（逾時、agent 錯誤、空的回覆）會直接讓整個 merge 失敗** ✅（這和 design 寫的一致）。
- A3（Medium）：問題是代價。一個 merge 有 N 個來源，最多 3N 次呼叫，每次最多 600 秒。第 k 個來源因為暫時性的問題失敗時，前面 k−1 個已經寫好、而且驗證過的要約都會被丟掉，下一次要全部重寫。**建議**：
  - 把已經寫好的 section 快取在 `<state>/summarize/cache/<來源 raw 的 md5>-<agent>-<prompt 版本>.json`（來源的 raw md5 沒變，就表示內容沒變），重新 merge 時直接沿用；merge 成功之後刪掉，或者保留 N 天；
  - 或者至少讓 `AgentError` 裡的「逾時」重試一次。
  - design 5.3 寫一句「N 個來源最多 3N 次呼叫」，並且在開始時印出來，讓使用者知道大概要等多久。

## 3. 巢狀的排版（A2、A7）

- 來源是 merge 時：`_require_sections` → `fetch_raw` → `json.loads(raw)["sections"]` → 放進 `sec["parts"]`；`_render` 遇到 `parts` 就用 `level + 1` 遞迴 ✅。不會出現循環（merge 只能指向已經存在的 Session）。
- **A2（Medium）**：沿用的 `sections.json` 沒有被驗證。已實測：`{"parts": [{"id": "agora:01Y"}]}`（缺少 `title`／`agent`／`summary`）→ `_render` 丟出 `KeyError: 'title'`。會遇到這種情況的有：手動修改過的 raw、以後 schema 改版（`prompt` 版本號會變）、或者存檔時的 bug。**建議**：再定義一個 `SECTIONS_SCHEMA`，用 `$defs` 遞迴：`section = {id, title, agent} 加上 (summary: SECTION_SCHEMA | parts: [section])`，二選一（`oneOf`）。在 **merge 存檔之前**，以及**沿用子 merge 的時候**都驗證一次；驗證不過，就丟出 InputError「`agora:X` 的 sections.json 格式不對，請重新 merge」。另外，`agora.merge.prompt` 和現在的 `SUMMARY_PROMPT_VERSION` 不同時，至少要印一行提示。
- A7（Low）：已實測，巢狀到第 5 層時，會出現 `#######`，超過 Markdown 的 6 層上限，就不會被當成標題了。建議 `level` 最多到 6，再往下改用粗體加縮排，或者在 merge 時就限制巢狀的深度。
- 同一個 Session 同時是直接來源，又出現在子 merge 裡面時（例如 merge(A, M)，而 M 裡面也有 A），A 會出現兩次。這和「照實展開」的語意一致，可以接受；如果要避免，可以在 design 寫明「不去重」。

## 4. 舊 merge 的拒絕 ✅

- `_require_sections`：只要 `agora.merge.kind` 不是 `sections`（第 5 版的全文串接沒有 `merge`，第 6 版是 `summary`），就丟出 InputError，並且印出完整的重新 merge 指令（列出它的 parents，加上 `--agent`）。**continue** 和**當成新 merge 的來源**這兩個地方都會呼叫它 ✅。

## 5. continue 改用 relation 判斷 ✅

- 以前是用「有沒有 `agora.raw`」來區分普通的 Session 和 merge；現在 merge 也有 raw 了（`sections.json`），所以必須改用 `relation == "merge"`，這個改法是對的。否則 merge 會被當成普通的 Session，把 `sections.json` 交給 `turns()` 去解析，結果就會失敗。
- merge 這條路：`_require_sections` → 用 `MERGE_NOTE` 加上排好的內文作為 user，`MERGE_READY` 作為 assistant → `native()` → `start_native`，和第 6 版相同 ✅。
- 小問題（Low）：merge 現在有 raw 了，`parent_md5` 卻還是記 `None`。改成 `md5(sections.json)` 的話，就和 C9／S7「記下實際接續的是哪一個版本」的原則一致了。

## 6. edit 對 merge 的 raw ✅

- `cmd_edit`：`raw = fetch_raw(...) if agora_of(old).get("raw") else None`。新的 merge 有 raw，所以會把 `sections.json` 原封不動地抓回來，用同一個 md5、同一個檔名重新 stage，push 時也不會把它刪掉 ✅。edit 只改標頭，內文是從 sections 排出來的，所以不會受影響 ✅（標頭的 `title` 改了，內文裡各節的標題也不會變，因為那些是來源的標題）。`show --raw` 印出的就是 `sections.json`，這很方便。
- 連帶要注意的地方：以前的 merge 沒有 raw，現在有了，所以「merge 沒有 raw」這個舊的前提，design 裡還有幾處要改（A9）。
