## Q1（Medium）：沒有符合的那段掃描，不會停

`find_in_agents` 只在兩個地方檢查 `is_cancelled`：換下一個 agent 之前，以及**每拿到一筆結果時**。可是兩個 adapter 的 `search_text` 都是「掃過整個資料、**找到符合的才 yield**」：
- opencode：兩輪 SQL，第二輪是全部掃過；
- claude：逐檔逐行讀 jsonl。

所以一段沒有符合的掃描（字打錯、或那個 agent 裡本來就沒有），從頭到尾都不會回到 `find_in_agents`，也就沒有機會停下來。

而防抖只擋得住「連續打字」。用輸入法的時候，每選完一個字、交出去之後，常常就停超過 0.3 秒，每一次停頓都會開一個新的掃描。

實測（pytest 裡的探測）：
- agent 的 `search_text` 做成「掃 2 秒、一筆都沒找到」（和真的 adapter 一樣，沒找到就不 yield）；
- 內文模式打 3 個字，每個字後面停 0.45 秒（模擬用輸入法選字）。

結果：開了 3 個掃描，**同時在跑的最多 3 個，3 個都跑到底**。

現在的測試 `test_a_search_that_is_replaced_stops_instead_of_running_to_the_end`，每 0.2 秒就 yield 一筆結果，正好碰不到這種情況。

**建議**（二選一，都不改「停打才搜」）：
1. **一次只跑一個**：還有掃描在跑的時候，不開新的，只記下「最新的字」；舊的跑完之後，最新的字和它不一樣，才再跑一次。這樣同時最多一個，而且最後一定是最新的字的結果；
2. **讓 adapter 也能停**：`search_text` 多收一個 `stop` 參數（例如 `lambda: worker.is_cancelled`），opencode 每讀 N 列、claude 每換一個檔案就檢查一次。

**加一個測試**：用「掃很久、不 yield」的假 agent，內文模式下打幾個字、每個之間停 0.4 秒，斷言同時在跑的最多 1 個（做法 1），或舊的掃描在被取代之後很快就結束了（做法 2）。

## Q2（Low）：停頓之前就按 Enter，會搜兩次

`filter_done` 會停掉計時器，**也會**在字和 `self.text` 不一樣時馬上搜一次。打完字不到 0.3 秒就按 Enter（打英文時很常見）：

但 mutation「Enter 不停掉計時器」**沒被抓到**：如果以後有人拿掉那幾行，就會變成 Enter 搜一次、計時器到了又搜一次。測試只在停頓之後才按 Enter，碰不到這種情況。

**建議**：加一個「打完馬上按 Enter」的測試，斷言只搜 1 次。

## Q3（Low）：T7 P3 還沒有測試

mutation「Esc 不清掉輸入框」還是沒被抓到。建議在 Esc 的測試裡斷言 `#filter` 的 `value == ""`。
