## P1（Medium）：內文模式每打一個字，就多一個 agent 搜尋同時在跑

`filter_typed` 每次都呼叫 `search(text)`。內文模式下，它會：
1. 在**主執行緒**查一次 Agora 的全文索引；
2. 開一個 `find_in_agents` 背景執行緒，去搜 opencode／claude 的資料（還沒快取的那些，要直接讀 agent 的資料）。

`find_in_agents` 是 `@work(thread=True, exclusive=True)`。但 Textual 的 `exclusive` 對執行緒只是把舊的「標成取消」，**不會讓它停下來**，而迴圈裡也沒有檢查是不是被取消了。舊的那幾個只是結果被 `found()` 丟掉，掃描本身照樣跑完。

實測（pytest 裡的探測）：
- agent 的 `search_text` 做成每次 1 秒（代替真的讀 agent 資料），20 個未匯入的 session；
- 打開篩選、ctrl+t 切到內文、打 `table`：

| | 結果 |
|---|---|
| 打 5 個字 | 開了 **5 個** agent 搜尋，**同時在跑的最多 5 個** |
| 再按 Enter | 又開了第 **6** 個：`filter_done` 用同樣的字再搜一次 |
| 主執行緒的全文索引查詢（30 個約 300 KB 的自編 Session） | 1～2 個字（不能用 trigram，要逐筆掃）每次約 10 ms；3 個字以上約 0 ms。這一部分還好 |

真的 agent 資料（opencode 的資料庫、claude 的 jsonl），沒快取時一次掃描可能要好幾秒。打一個英文詞就是好幾個同時在掃，CPU 和磁碟都被占住。T2 的回饋 9 就是因為內文搜尋慢，才改成「邊找邊出現」的。

用輸入法打中文時，一個詞通常只交出一兩次（選完字才交），所以影響比較小；打英文、數字、或逐字選字時就很明顯。

**建議**（不改「邊打邊篩」的做法）：
- **內文模式加防抖**：和預覽一樣，最後一次改動之後約 300 ms 沒有再打字，才開始搜；標題模式照舊逐字篩（在記憶體裡，很快）；
- `find_in_agents` 在每個 agent、每一筆結果之間檢查 `get_current_worker().is_cancelled`，被取代了就停；
- `filter_done`：字和 `self.text` 一樣時，不要再搜一次；
- **加一個測試**：內文模式下快速打 5 個字，斷言 agent 的 `search_text` 只被呼叫 1 次（或同時在跑的不超過 1 個）。
