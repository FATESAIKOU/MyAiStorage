**High 一個（H1）：背景上傳在「驗完 md5 之後」用 `rmtree` 刪掉 outbox 的那一筆，這時前景可能已經又 stage 了同一個 Session 的新版本（例如 import 之後馬上 edit），新版本會被刪掉，之後同步時本機的鏡像還會被 Drive 上的舊版蓋回去。** 有了背景上傳之後，這從「兩個前景指令剛好同時跑」的罕見情況，變成了「import 完馬上 edit」的日常情況。實作之前，design 要先定好規則：只刪掉**自己驗過的那個版本**。

另外有 7 個 Medium：
- **M1**：前景的 `push`／sync 和背景上傳，沒有說好要共用同一把鎖；
- **M2**：exit code 3 的意思會變；
- **M3**：`_upload` 走 `main()` 的時候，會先跑 `recover_pending`；
- **M4**：原始檔那一輪只成功了一部分的時候，順序的保證就不見了；
- **M5**：`pull` 會把排隊等著刪除的 Session 拉回來；
- **M6**：proposal 寫「Modified Capabilities：無」，但其實改到了 batch-commands；
- **M7**：tasks 的 2.3／3.1、2.2／3.2 會讓兩個人改同一段程式。

## (1) spec 的矛盾和漏掉的情況

### H1（High）：背景上傳刪掉 outbox 時，會把剛 stage 進來的新版本一起刪掉

**現在的程式**：`push_one` 先上傳、驗 md5，然後 `shutil.rmtree(folder)`。而 `stage` 是用「舊的改名到一邊、新的搬進來」的方式換掉 `outbox/<ULID>`。

**T3 之後會發生的事**：
1. import X，存進 outbox，背景開始上傳 X 的 v1；
2. 使用者馬上 `edit X`，`stage` 把 `outbox/X` 換成 v2，`remember` 把 v2 的 session.md 放進鏡像和索引；
3. 背景驗完 v1 的 md5（Drive 上的 v1 和它手上的清單一致），接著 `rmtree(outbox/X)`，**刪掉的是 v2**；
4. v2 從來沒有上傳過，outbox 裡也沒有了。下一次同步看到 Drive 上 session.md 的 md5 是 v1 的、和索引裡記的 v2 不一樣，就把 **v1 下載下來蓋掉鏡像裡的 v2**。edit 就這樣不見了。

批次上傳讓這個空檔更大：從第一次 copy 到最後列檔驗 md5，中間有好幾次 rclone，每一次都要 1～50 秒。

**design 要寫清楚**：離開 outbox 的條件，是「outbox 裡**現在**的 session.md 的 md5，等於 Drive 上的、也等於這一輪上傳的那一個」。而且要用**原子**的方式做：先把 `outbox/X` 改名成 `outbox/.done-X`，再比對 md5，相符才刪；不相符就改名回去。stage 那一邊也要能處理 `.done-X` 存在的情況。另外補一個測試：上傳中途 stage 一個新版本，斷言新版本還在 outbox 裡，之後也會被傳上去。

### M1（Medium）：前景的 push／sync 和背景上傳要共用同一把鎖

design 寫的是 `push_outbox` 和 `push session` 都用新的批次上傳，但**只有 `_upload` 會拿 `upload.lock`**。如果背景正在傳，這時候前景執行 `agora push session X`（spec 說它會等到傳完），或者任何指令的 sync 裡呼叫了 `push_outbox`，就會有**兩個**上傳的程序同時傳同一批東西、同時 `rmtree`（讓 H1 更容易發生）。

**建議**：
- **所有**會上傳 outbox 的地方（背景的 `_upload`、sync 裡的 `push_outbox`、`push`）都拿同一把鎖；
- 前景的 `push` 用**阻塞**的方式等鎖（加上逾時與提示「背景上傳中，等它…」），sync 則用非阻塞：拿不到鎖就跳過 outbox，交給正在跑的那一個；
- spec 的「背景上傳」那一段，也要寫一句「同一時間只有一個上傳，**不論前景或背景**」。

### M2（Medium）：exit code 3 會變成每一次都是

現在 `_emit` 在「沒有傳上去」時回傳 `EXIT_IN_OUTBOX`（3）。T3 之後，存完本機就結束，所以每一次 import、continue、merge 都會是「還在 outbox」，也就都是 exit 3。這和主規格 batch-commands 的「全部成功是 0」衝突；互動模式的結果視窗也是看 `code == 3` 來決定說「已存進 outbox，之後的指令會自動再送」。

**要決定**：已經交給背景的，算成功（exit 0），結果視窗說「已經存在本機，背景上傳中」（spec 已經這樣寫了）；那 3 還要不要留？例如「背景上傳**啟動失敗**」時才用。spec 和 design 都沒有提到。互動模式的 4.1 也要依這個決定來寫，不能再用 `code == 3` 判斷。

### M3（Medium）：`_upload` 不能走 `main()` 的開場

`cli.main` 在每一個動作之前，都會先跑 `recover_pending`（收尾中斷的接續，會呼叫 agent 的 `collect`，可能還會再 `_save`、再 spawn 一個背景上傳），再印 outbox 和壞檔的提醒。如果 `_upload` 只是 `ACTIONS` 裡的一個動作，背景程序就會：
- 在背景裡叫 agent；
- 在自己裡面再 spawn 一個自己（遞迴）；
- 而且 `choices=list(ACTIONS)` 會讓它出現在 `--help` 和錯誤訊息裡。

**建議**：用一個**獨立的模組入口**（例如 `python -m agora.background`），不經過 `main()`、不經過 argparse，只做上傳和刪除佇列。

### M4（Medium）：原始檔那一輪只成功了一部分時

spec 寫「原始檔都到了之後，一次上傳全部的 session.md」。但 `rclone copy --files-from` 傳到一半失敗時，是一部分傳上去了、exit 不是 0。design 沒有說這時候第二輪要怎麼做。如果照樣傳全部的 session.md，就會有 session.md 比它的原始檔先到 Drive 的情況（讀的一方會因為 G3 跳過它，所以不會讀錯，但「先原始檔、後 session.md」的保證就沒有了）。

**建議**：二選一，寫進 design。
- (a) 原始檔那一輪不是 exit 0，就**整批都不傳 session.md**，等下一輪；
- (b) 在兩輪之間列一次檔，只傳原始檔確定已經在 Drive 上的那些 session.md（多一次呼叫）。

(a) 比較簡單，也符合「固定幾次」的說法。

### M5（Medium）：`pull` 會把排隊等著刪除的 Session 拉回來

spec 只說**同步**不能把 trash-queue 裡的加回來。但 `pull session X` 也會：X 已經被 `forget_local` 了，Drive 上還在（還沒 purge），`_pull_agora` 就會照常下載 session.md、放進索引，X 就回到本機了。之後背景 purge 了 Drive 上的那一個，本機這一份就變成「雲端沒有」。

**建議**：spec 加一句「在刪除佇列裡的 Session，`pull` MUST 拒絕（說『正在刪除』）」，或者乾脆當成找不到。`_lost_in_cloud`、`push --not-exist-upload` 也一樣要看佇列。

### 其他漏掉的情況（Low～Medium）

| # | 情況 | 建議 |
|---|---|---|
| L1 | **continue、edit 還是會在前景連 Drive**：`_refuse_if_gone` 在開始前、`_finish` 在結束時、edit 在存檔前，都會做一次完整的列檔（M1、F1、F8，T1 的決定）。所以「不用等」對 continue、edit 只是一部分；spec 只寫了 import、continue、merge 不等上傳 | 在 spec 或 design 寫明「寫回既有 id 前的雲端檢查照舊在前景」；或者如果要改，就要重新決定 T1 的 M1，這是使用者的決定 |
| L2 | **edit 也會變成背景上傳**（它也走 `_save`），可是 spec 和 tasks 都只寫了 import、continue、merge | 明確寫上 edit（以及 `recover_pending` 的收尾） |
| L3 | **同一個 Session 同時在 outbox 和刪除佇列裡**（例如 edit 之後馬上 delete）：design 的順序是先上傳、再刪除，所以會先把它傳上去，再移到垃圾桶 | `_upload` 處理 outbox 時，跳過刪除佇列裡的 ULID；或者 delete 的時候直接把 outbox 裡的那一筆也拿掉（現在的 `delete_session` 本來就有 `rmtree(outbox/<ulid>)`） |

| L5 | **「outbox 有 N 筆未上傳」的提醒會變成噪音**：import 完馬上 `search`，背景還在傳，每個指令都會說「outbox 有 3 筆未上傳」，看起來像是出了錯 | 鎖被拿著的時候（背景正在傳），改成說「背景上傳中，N 筆」；只有鎖沒人拿、outbox 卻不是空的時候，才說「沒上傳成功」 |

## (2) design 的做法可不可行

| 做法 | 看法 |
|---|---|
| `rclone copy <outbox> gdrive:sessions --files-from <清單> --no-traverse` | **可行**。現在的 `download_many` 就是反方向的同一種用法（`copy gdrive:sessions <mirror> --files-from … --no-traverse`）。清單裡的路徑是相對於來源 `<outbox>` 的 `<ULID>/raw-….json`；目的地需要的 `sessions/<ULID>/` 資料夾，rclone 會自己建 |
| 兩輪分開（原始檔、session.md） | 對，而且還有一個 design 沒寫到的好處：Drive **允許同名的資料夾**。如果同一輪裡同時有兩個檔案要建同一個新的 `<ULID>/`（`--transfers` 預設是 4），有機會建出兩個同名的 `<ULID>` 資料夾。分兩輪之後，每個新 ULID 在第一輪都只有一個檔，就避開了 |
| `copy` 判斷要不要傳 | `rclone copy` 預設看「大小加修改時間」，一樣就跳過。session.md 每次 stage 都是新寫的檔案，修改時間會變，所以實際上會傳；但為了確定，建議第二輪加上 `--ignore-times`（一律傳），或者用 `--checksum`（Drive 有 md5） |
| 「固定幾次 rclone」和配額 | ⚠️ rclone 內建 client 的共用配額，算的是 **API 請求**，不是 process 的數量。`--no-traverse` 加上 `--files-from`，對每一個檔案都還是會在 Drive 上查一次「有沒有這個檔」，每個新 ULID 也要查或建一次資料夾。所以「一批 4 次 rclone」大約還是 2N 個以上的 API 請求，只是少了每個 process 啟動和換 token 的成本。這不影響做法，但 PM 實跑時（5.3），建議也用 `-v --stats` 或 `--dump headers` 量 **API 請求的數量**，不要只數 process |
| `rclone delete --files-from` 清掉舊的原始檔 | 可行。要刪的名字來自第三步的列檔（Drive 上有、但不是標頭指到的 `raw-*`），和現在 `push_one` 的邏輯一樣 |
| flock 與晚到的 Session | 鎖可行（macOS 和 Linux 都是 BSD flock，以 open file description 為單位，T2 已經實測過）。design 自己指出的那個空檔（最後一次檢查之後、放開鎖之前才進來的），**其實可以關掉**：放開鎖之後**再檢查一次** outbox 和佇列，不是空的就再拿一次鎖、再跑一輪。因為 stage 一定先寫 outbox、再 spawn，所以「正在跑的那一個在放開鎖之後看到」和「新的那一個拿得到鎖」，至少會有一個成立。這樣就不用把晚到的交給「下一個指令」 |
| 背景程序不接 pipe | `stdin=DEVNULL`、stdout／stderr 寫到 `upload.log`、`start_new_session=True` 都對。**還要**確認 `close_fds=True`（Popen 的預設值，不要改掉）：continue 在 `_finish` 的時候還拿著 **pending 的鎖**（`lock` 要等 `pending.unlink()` 之後才 close），如果背景程序繼承了那個 fd，G1 的 `continuing()` 就會一直以為「正在接續」。env 要原封不動地傳下去（`AGORA_FOLDER_NAME`、`AGORA_CACHE_DIR` 等等），否則背景會傳到正式的 `agora/` |
| `remember` 也複製原始檔 | sync **每一次**都會對 outbox 裡的每一筆呼叫 `remember`（`_index_outbox`），所以要「同名、同大小就不複製」，並且用原子寫入（見 `docs/review/P1-options.md`）。design 裡沒有寫 |
| `upload.log` 附加寫入 | 會一直變大。建議每次啟動時，超過一定大小（例如 1 MB）就只保留尾巴 |
| 測試 | 現在有上百個單元測試，都假設 import 結束時 Drive 上已經有了。design 說「單元測試直接呼叫上傳函式」，但這些既有的測試要怎麼改，沒有寫。建議做一個開關（例如環境變數 `AGORA_UPLOAD=inline`，或者 monkeypatch spawn 的那個函式），讓測試和需要確定結果的腳本可以在前景同步地上傳；整合測試也需要一個「等背景傳完」的 helper（等鎖被放開，而且 outbox 是空的） |

## (3) 和主規格的衝突

| 主規格 | 衝突的地方 | 建議 |
|---|---|---|
| `batch-commands`「import 一次多個」：「MUST **先同步一次**，再逐一匯入」 | T3 把它改成受 5 分鐘節流，等於「可能不同步」 | 這是**修改**既有的 Requirement，proposal 的「Modified Capabilities：無」不對，要加一個 `batch-commands` 的 MODIFIED delta |
| `batch-commands`「import 一次多個」：「exit code 是第一個非零的（全部成功是 0）」 | M2：存進 outbox 就回傳 3 的話，每一次都會是 3 | 同上，在 delta 裡寫明「交給背景就算成功」 |
| `session-sync`「push 只寫回該寫的檔案」：「MUST 先送出 outbox，再…」 | 背景正在送 outbox 的時候，push 要等它還是自己送？ | M1 的鎖；在 delta（或 T3 的 spec）裡寫清楚 |
| `session-sync`「pull 只處理給的 id」 | M5：在刪除佇列裡的，pull 會把它拉回來 | 在 T3 的 spec 加上 pull 的例外，或者加一個 `session-sync` 的 MODIFIED delta |
| `session-sync`「雲端沒有的 Session 保留在本機並標記」 | 不衝突：在佇列裡的已經 `forget_local` 了，不算「本機有」。T3 的「不標記」只要保證 sync 不會把它加回來就好 | — |
| `batch-commands`「delete 重跑略過已刪除」 | 不衝突：墓碑在前景就寫了。但如果背景一直刪不掉，重跑會說「已經不在了」，而 Drive 上其實還在；所以要靠 L4 的提醒 | — |

## (4) tasks 的分工

| 衝突點 | 誰 | 位置 | 建議 |
|---|---|---|---|

| spawn 背景程序的那個 helper | impl2（2.4）、impl1（3.1 的 delete 也要 spawn） | 同一個 helper | 在 2.3 一起做好，impl1 只呼叫它 |

## 結論

方向可行，rclone 的用法也都有前例。**實作之前**，design 和 spec 要先補上：
1. H1 的「只刪掉自己驗過的那個版本」；
2. M1 的鎖（所有會上傳 outbox 的地方共用同一把鎖，前景的 push 要等它）；
3. M2 的 exit code；
4. M3 的獨立入口；
5. M4 的部分失敗；
6. M5 的 pull 例外；
7. M6，proposal 補上 batch-commands（以及可能的 session-sync）的 MODIFIED delta；
8. tasks 照 (4) 的建議調整分工。

Low 的那幾項，可以在實作時一起處理。
